# Pattern: Site archetypes (multi-page composition)

**Inherits:** all of `fundamentals.md` — especially **F74** (one set of measures on one axis) and F50–F53 (reflow). Composes the single-screen patterns — `marketing.md` (P-M), `dashboard.md` (P-D), `detail.md` (P-DT), `list.md` (P-L), `form.md` (P-F) — into multi-page wholes; **references them, never restates them.**
**Cite as:** `P-SA-<nn>`.

> **The multi-page extension of `layout.md`.** `layout.md` (P-LY) owns how *one* blank page divides into regions; this owns how *many* pages compose into one coherent product. The seam is exact: P-LY-05/F74 make the alignment spine hold *down a page*; this makes the shell and the spine hold *across pages*. Almost every surface in this brain is single-screen, so this file is **deliberately tiny — three rules.** It earns its place only by owning the things no single-screen pattern and no fundamental can: **(a) which whole-product shell wraps the pages, (b) the one invariant F74's per-page check structurally cannot see — the container axis wandering *between* pages, and (c) the supporting pages (settings / docs / legal / changelog / 404) that are the real coherence test.** Everything else about how pages relate — the nav model, the persistent/contextual chrome split, breadcrumb/back paths — is already owned by `layout.md` (P-LY-03), `containers.md`, and general IA, and is NOT restated here. Read this once per *product* (not per page), at approach-time, right after `approach.md` picks the site shape.

## Surface intent
A product is not its best page — it is whether the changelog, the settings screen, the pricing table, and the 404 all feel like the same place. Coherence across pages is a different failure mode from coherence within a page: each page can be individually excellent and the product still read as assembled from unrelated templates because the shell changed, the container width hopped between pages, or the supporting pages dropped the brand. The job here is narrow and specific: pick **one of four whole-product shells** by the product's job (`P-AP-03`), hold **one container axis + one type rhythm** across *every* page (the cross-page extension of F74), and make the **supporting pages live inside that same shell**. The dynamic insight mirrors P-LY-01: the shell falls out of *who shows up and what they're doing* — convince-a-visitor ⇒ marketing shell; operate-on-data ⇒ web-app shell; learn-the-product ⇒ docs shell; monitor-then-drill ⇒ dashboard product.

## Density band
**No density of its own — each page keeps its archetype's band (F26), and the shell keeps ONE chrome density site-wide.** A marketing shell's nav is airy; a product shell's sidebar is compact; whichever it is, it is identical on every page. The one cross-page density rule: settings/docs/detail pages inside a product shell inherit the *product's* density, never marketing whitespace dropped into a compact app (the cross-page face of the F26 tell, enforced by P-SA-03).

## Calibrations

**P-SA-01. Pick ONE of four whole-product shells from the job, at approach-time — then every page lives inside it. Marketing site (convince a visitor) · web-app shell (operate on data/records) · docs site (learn/reference the product) · dashboard product (monitor then drill).** A product may host *more than one* shell (a marketing site + the logged-in app + docs), but each is a distinct zone with a clear seam, and any given page belongs to exactly one.
New (formalizes gallery → SiteArchetypes site-shape + `P-AP-03` content-shape, extended to multi-page). *Why:* the shell is the largest composition decision and the one most often defaulted — a top nav forced onto a 12-destination app, or a sidebar bolted onto a five-page brochure, is the genericness tell at product scale. The shell is chosen by *who's looking and where they are*, not the page topic: a logged-out visitor sees the marketing shell, a logged-in user sees the app shell — even for the *same* concept (e.g. a product that renders pricing inside the marketing top-nav for visitors and inside the app's left-sidebar for logged-in users — `evidence/site-archetypes.md`). The nav model *within* a chosen shell is `P-LY-03`'s job (sidebar-vs-topbar), held identical across the shell's pages — this rule only picks the shell. *Check:* name the one shell each page belongs to, and the one sentence of job/audience that chose it; no top-nav on a deep-nav app, no sidebar on a brochure.

**P-SA-02. ONE container axis and ONE type rhythm are SITE-WIDE invariants, not per-page — F74 holds across pages, not just down one.** The ≤3 sanctioned measures on one axis (F74 / `P-LY-05`) are chosen once for the whole product; the home hero, the pricing table, the settings form, and the 404 all return to the same axis and the same display+body type scale. A page picks *which* of the ≤3 measures it uses; it does not invent a fourth or shift the axis.
Refines: **F74**, `P-LY-05`. *Why:* this is the one place F74 genuinely needs extension — its `Check:` traces the left edge *down a page*, which passes even when page A is 1100px-centered and page B is 1280px-left-flush. The wandering edge across *pages* (AP21 at product scale) is invisible to every single-page sweep, so it needs its own cross-page check. Real products hold the measure site-wide: marketing home/pricing share one centered column; docs prose holds ~680px on every article (`evidence/site-archetypes.md`). *Check:* list the content width + axis of one page per archetype in the product (home, a record, settings, a docs article) — all resolve to the same ≤3 measures on the same axis, and the display+body type scale is identical across them.

**P-SA-03. Settings, docs, legal, changelog, and 404 live INSIDE the product's shell and brand — same shell, container axis, type, and accent as the marketing/app pages. The supporting pages are the coherence test.** Settings opens in the app's shell (often with a nested settings sub-nav), not a bare page; legal/changelog use the same body type as the blog; the 404 uses the display type and accent of the homepage. None of these is a different site.
New (distills gallery → SiteArchetypes "the supporting pages are the brand test" + `evidence/layout.md` settings-in-shell). *Why:* anyone can make the homepage cohere; the career-level signal is whether the changelog and the 404 feel like the same product. These pages are where AI/template output most often drops the shell and resets the type — the exact spot the "one system vs a campaign" distinction shows. Reinforces `P-AP-03`/P-SA-02: their density and axis are the *product's*, never marketing whitespace in a compact app, never a fresh container width. *Check:* settings/docs/legal/changelog/404 each carry the product's shell, container axis, type scale, and accent — none reads as a separate site.

## Composition defaults
- **Run order (once per product, at approach-time):** `approach.md` picks the site shape → **P-SA-01** picks the shell(s) → `P-LY-03` fixes the one nav model for each shell (held identical across its pages) → **P-SA-02** fixes the one container axis + type rhythm site-wide → then each page is composed with its single-screen pattern + the 2–3 directions (`SKILL` protocol) → **P-SA-03** holds the supporting pages inside the same shell. The shell and invariants are decided *before* any page.
- **The four shells (decision guidance):**
  - **Marketing site** — top nav (≤6 links + one CTA verb, `P-M-03`) + footer sitemap. Pages: home/features/pricing/about/blog/changelog/contact, each a single-screen recipe (`marketing.md`, `pricing.md`). Variety lives in section rhythm per page (`P-M-09`), not in the chrome.
  - **Web-app shell** — left sidebar (grouped nav, `P-LY-03`) + top-right global search/account. Content area cycles through list (`P-L`) / detail (`P-DT`) / form-settings (`P-F`) recipes.
  - **Docs site** — left category tree (~200–260px) + top-level switcher (Guides | Reference) + persistent `⌘K` search + right TOC. Pages: docs-home (wayfinding) + docs-article (three-zone: tree · ~680px prose · sticky TOC).
  - **Dashboard product** — the web-app shell, data-led: overview (`P-D`) → drill-down (`P-DT`) → settings (`P-F`), one shell.
- **The single invariant across all four:** one shell + one container axis + one type rhythm, held on every page (P-SA-02); the page interior is where the single-screen patterns and the 2–3 directions vary.
- **Reflow:** the shell collapses per `mobile.md` (sidebar → drawer, top nav → hamburger, docs tree → button, TOC → below title) — every page in a shell collapses the *same* way, so mobile coherence holds too.

## Forbidden moves
- **A wandering container axis across pages** — page A 1100-centered, page B 1280-left-flush; AP21 at product scale, invisible to the single-page F74 sweep (`P-SA-02`).
- **The type rhythm resetting between pages** — a different display face or body scale on the blog vs the app vs the docs (`P-SA-02`).
- **A top nav forced onto a deep-nav (>~5 destinations) product app, or a sidebar bolted onto a five-page brochure** — wrong shell for the job (`P-SA-01`; `P-LY-03`).
- **Settings/docs/legal/changelog/404 as a different site** — bare page, reset type, marketing whitespace in a compact app, no shell (`P-SA-03`).
- **Re-deciding the shell or invariants per page** — these are product-level invariants; only the page interior varies (mirrors `P-AP-10` — diverge on composition, converge on the system).
- **Restating single-screen anatomy here** — hero shape, KPI count, nav model, breadcrumb internals belong to their own patterns (`marketing.md`, `P-LY-03`, `containers.md`); this file owns only the shell choice, the cross-page axis, and the supporting-page coherence.
