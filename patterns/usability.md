# Pattern: Usability (ease & felt-quality — the cost of *using* this)

**Inherits:** all of `fundamentals.md` unless overridden below — especially F52 (Fitts/Hick), F26 (density), F12–F14 (hierarchy), F33 (the four data states), F67–F69 (copy/error tone). This pattern operationalizes the *named usability laws* behind those rules and adds the operational gaps.
**Cite as:** `P-UX-<nn>`.

> **Cross-cutting pattern — the ease-of-use layer.** Lookbook already systematizes most of usability *implicitly*: contrast (F15/F54/F55/F66 + `scripts/contrast.mjs`), the four data states (`patterns/states.md` / F33), accessibility semantics (`patterns/accessibility.md` / P-AY), motion (`patterns/motion.md` / P-MT), forms (`patterns/form.md` / P-F), empty states (`patterns/empty-states.md` / P-ES); system-status feedback lives within `patterns/states.md`. This file is the **consolidating spine that names the laws** — Nielsen's heuristics, Jakob's/Hick's/Tesler's/Doherty's laws, Krug's clarity test, the response-time limits — and **fills the gaps those files don't own**: good defaults, progressive disclosure, error *prevention*, forgiveness-over-confirmation, perceived performance, the latency budget. Load it on any surface a human has to *operate* — i.e. nearly all of them. It does **not** duplicate the cross-cutting files; it cross-references them and adds the missing operational rules. The behavioural/motivation layer (habit, engagement, the ethical line) lives in its sibling `patterns/engagement.md` (P-EN).

## Surface intent
Usability answers one question for every user, expert or first-timer: **how much does it cost me — in attention, memory, steps, and risk — to get what I came for?** The failures here are not taste calls; they are *taxes*: a value the user must remember instead of being shown, a wall of equal-weight choices, a destructive action with no undo, a multi-second wait with no status, a primary action you can't find. Each tax is small and each is shipped constantly by AI-built UI because the *obvious* implementation skips the cheaper-for-the-user path. The reference frame is **canon**: Nielsen's 10 usability heuristics, NN/g's body of research, the Laws of UX (Jakob, Hick, Fitts, Doherty, Goal-Gradient, Tesler, Postel, Miller), Krug's *Don't Make Me Think*, and the Card/Moran/Newell + Miller response-time limits. The north star: **the system absorbs complexity so the user doesn't have to** (Tesler).

## Density band
**No density of its own — applies at every band.** A compact dashboard and a spacious wizard carry the same usability obligations: visible status, recoverable actions, sensible defaults, a findable primary action. Density tunes *how much* is on screen (F26); usability governs *how it behaves* regardless. The one intersection is cognitive load (P-UX-02): higher density raises the bar for grouping and staging, never lowers it.

## Calibrations

**P-UX-01. Recognition over recall (Jakob Nielsen, heuristic #6). Surface options, state, and previously-entered values in the interface; never make the user remember information from one part of the UI to use it in another. Actions and choices are visible/retrievable, not memorized.**
New. *Why:* working memory is scarce and effortful; recognition (seeing the option) is far cheaper than recall (remembering it). Hidden state — a mode the user must remember they're in, a value typed two steps ago, a command that must be memorized — taxes memory and causes errors. Visible menus beat memorized commands; showing the active filters beats remembering them; carrying a known value forward beats re-asking. A command palette is recognition-friendly *because* it lets users find an action by name instead of memorizing a shortcut.
*Check:* no step requires the user to hold a value from a prior step in their head — it's carried forward or shown; current mode/selection/filter state is always visible on screen; commands/actions are discoverable (menu, palette, labelled control), not memory-gated; previously-entered data is pre-filled, not re-requested.

**P-UX-02. Cognitive-load budget (Hick's Law; Miller's ~7±2; Tesler's Law of conservation of complexity). Cap the choices competing for attention at once; group and stage. Inherent complexity can be moved but not deleted — the system absorbs what it can, the user bears the rest only when the choice genuinely matters.**
Refines: F52 (Fitts/Hick), F26 (density). *Why:* Hick's Law — decision time grows with the log of the number of options, so a flat 20-item menu is slower and more error-prone than 4 labelled clusters. Miller's ~7±2 is a rough working-memory ceiling (the honest modern read: *chunking* matters more than the exact number — group, don't just count). Tesler: every product has irreducible complexity; the only question is *who bears it*. Dumping it on the user (a wall of toggles, manual setup) is the lazy default; absorbing it (smart defaults, disclosure, sensible automation) is the design work.
*Check:* count the choices presented simultaneously; when a surface exceeds a comfortable cluster, group (~5–9 per group, grouped not flat) and/or stage (P-UX-04); for any complexity, confirm the system absorbs what it can (defaults P-UX-03, disclosure P-UX-04) before exposing it; no flat mega-menu where grouping would halve the decision.

**P-UX-03. Good defaults (choice architecture — Thaler & Sunstein). Pre-select the safest, most common, reversible option. Asking the user to choose has a cost — spend it only where the choice genuinely matters to them.**
New. *Why:* defaults are powerful — most users keep them — so the cheapest interaction is the one the default removes entirely. A good default is *safe* (low blast radius if wrong), *common* (right for most), and *reversible* (cheap to change). The line to hold: a default must serve the **user's** interest. A default pre-ticked to benefit the business over the user (an opt-in to marketing, a costlier plan pre-selected) is not a "good default" — it's the **preselection** deceptive pattern (P-EN-11).
*Check:* every optional choice has a sensible pre-selected default; the default is the safe + common + reversible option; mandatory (un-defaulted) choices are reserved for decisions the user actually cares about; no default silently serves business-over-user interest (cross-ref P-EN-11 preselection).

**P-UX-04. Progressive disclosure (NN/g). Show the few most-important options first; reveal the advanced/rare set on demand. Keep it to ≤2 levels — primary now, secondary one obvious step away.**
New. *Why:* front-loading every option overwhelms novices and slows experts; deferring advanced features lowers cognitive load and improves three of usability's components at once — learnability, efficiency, and error rate (NN/g). Beyond two levels users get lost, so the primary→secondary path must be obvious; and *placing* a control in the primary view is itself a signal that it's important (use that deliberately). **Honest grounding caveat:** the strongest *empirical* backing is Carroll's IBM "training wheels" study on a single word processor; the broader principle is widely accepted but lightly RCT'd — see `evidence/usability.md`. The failure mode is over-hiding to "look simple" or hiding features to serve business goals rather than user tasks.
*Check:* the initial view shows only common-case controls; advanced/rare options live one obvious step away (a "More", an expander, a secondary panel) — not buried, not three levels deep; disclosure depth ≤2; nothing the *common* task needs is hidden behind disclosure.

**P-UX-05. Error prevention by constraint (Nielsen heuristic #5; poka-yoke; Postel's robustness for input). Prevent the error before it can happen — constrain inputs to valid values, disable impossible actions, accept forgiving input formats and normalize them. Prevention beats even the best error message.**
Refines: `patterns/states.md` (error states), F69 (error copy), `patterns/form.md` (P-F). *Why:* Nielsen ranks error *prevention* above good error messages — the best error is the one that can't occur. A date picker can't yield Feb 31; a "Submit" disabled-until-valid can't submit garbage; a phone field that accepts `(415) 555-1234`, `4155551234`, and `+1 415 555 1234` interchangeably (forgiving format, then normalize) removes a whole class of rejection. Poka-yoke: make the wrong action structurally impossible rather than warning after the fact.
*Check:* invalid states are unreachable where feasible (constrained pickers, type-appropriate inputs, disabled-until-valid); inputs accept reasonable format variants and normalize rather than reject; irreversible/destructive actions are guarded (→ P-UX-06); the errors that *remain* still get F69 problem-and-fix copy, programmatically associated (P-AY-07).

**P-UX-06. Forgiveness over confirmation (Nielsen heuristic #3, user control & freedom; undo > "are you sure?"). Default to reversible actions with undo, not blocking confirmation. Non-destructive defaults, autosave, and version history make the product safe to explore fast.**
New. *Why:* a confirmation dialog taxes *every* action — including the 99% that were intentional — and trains users to click through it blindly, so it stops protecting anyone. Undo taxes only the rare mistake. Gmail's Undo Send *delays* the real send for ~5–30s so it stays cancellable; Figma's version history makes any prior state recoverable; both let users move fast because nothing is fatal. Reserve hard confirmation for genuinely irreversible, high-blast-radius actions (permanent delete, sending money) — and even there prefer type-to-confirm over a reflexive "OK". **Consistency matters:** undo on some deletes but a confirm on others gives an unreliable safety signal. **The single most common instance — name it explicitly: a form or modal with unsaved input.** Cancelling or closing a partially-filled form silently *discards work* — that is a destructive, irreversible action wearing an innocent label. Guard it: a "Discard unsaved changes?" confirm fired only when the form is *dirty*, and/or an autosaved draft so the input survives. Don't drop entered data on cancel/close. (This is exactly the gap a real build ships — a Cancel button that throws away ten filled fields with no prompt.)
*Check:* reversible actions use an undo affordance (a toast with Undo), not a confirm dialog; work is autosaved/recoverable (drafts, version history); **a form/modal with unsaved edits guards its discard — a dirty-state "Discard changes?" confirm or an autosaved draft — never silently losing entered data on cancel/close**; confirmation is reserved for irreversible high-stakes actions *and is consistent* across the app; no destructive default (the safe state is the default, P-UX-03).

**P-UX-07. Visibility of system status within the latency budget (Nielsen heuristic #1; response-time limits 0.1s / 1s / 10s — Miller 1968, Card et al. 1991; the Doherty Threshold, IBM 1982). Always show what the system is doing, within human time thresholds; aim under ~400ms for core actions to keep users in flow.**
Refines/consolidates: `patterns/states.md` (loading states + system-status feedback) — **this adds the numeric budget.** *Why:* the limits are perceptual and have held for decades — **<0.1s** feels instantaneous (action and result read as causally linked; no feedback needed beyond showing the result); **<1s** keeps the flow of thought (delay is noticed, but no spinner needed); **>1s** needs a visible indicator; **>10s** needs a percent-done progress bar and the freedom to keep working or the user task-switches. The **Doherty Threshold**: productivity and engagement keep *rising* as response drops toward ~400ms, where users enter flow (Buchheit's 100ms "instant" Gmail bar; Amazon's "100ms = 1% sales" is the same physics). Status feedback also prevents duplicate actions (the double-submit when unsure the first click registered) and builds the sense of control that earns trust.
*Check:* every action gives feedback within its threshold — instant (<100ms) needs only the result; >1s shows a spinner/inline indicator (P-ST); >10s shows percent-done + keeps the UI usable; **measure real interaction latency (round-trip + render, not server time alone)** and target <400ms for core actions; no action ever leaves the user unsure whether it registered.

**P-UX-08. Perceived performance (NN/g skeleton-screen research; optimistic UI; Goal-Gradient progress — Kivetz et al. 2006). Manage the *feeling* of speed, not only the milliseconds. Skeletons for full-layout loads, spinners for small/indeterminate waits, optimistic UI for safe reversible actions, honest progress for long jobs.**
Refines: `patterns/states.md` (loading), P-UX-07. *Why:* a spinner is information-free — every second looks identical, so the wait feels *longer* than it is. A skeleton shows the page's structure arriving, shifting the user from waiting to anticipating; Facebook and LinkedIn report large *perceived*-performance gains with no backend change. Optimistic UI reflects the result immediately and rolls back only on the rare failure, erasing the perceived round-trip for the >95% success path (Linear, Superhuman). Goal-Gradient: people accelerate toward a *visible* goal, so an honest progress bar both reassures and motivates. **The constraints (where teams get it wrong):** don't skeleton sub-~1s loads (the flash is jarring); don't show a bare header/footer "frame" with no content placeholders (reads as broken); never optimistic-UI a non-idempotent or high-stakes action (payment, permanent delete) where rollback is disorienting or impossible.
*Check:* full-page/layout loads use a skeleton that matches the real layout (not a bare frame, not under ~1s); small/indeterminate waits use a spinner; safe reversible mutations reflect instantly with rollback-on-error (and the error is *announced* — P-AY-08); long jobs show real percent-done; no optimistic UI on payments/destructive actions.

**P-UX-09. One primary action per screen (Steve Krug, *Don't Make Me Think*; the clarity test). Each screen or step has exactly one visually-dominant primary action; everything else steps down. A new user should identify the next step in under ~2 seconds.**
Refines: F12–F14 (hierarchy); the depth rubric's "compositional anchor". *Why:* the brain can't prioritize competing stimuli of equal visual weight — the "everything is important" screen reads as "nothing is important," and users scan past all of it. One loud primary action (size + weight + colour + isolation) decodes intent instantly; secondary and tertiary actions are quieter by design. This is the interaction-layer twin of the hierarchy fundamentals: hierarchy for *comprehension*, one-primary-action for *what to do next*.
*Check:* exactly one primary-styled action per screen/step; secondary actions are visibly subordinate (ghost/text vs filled); the "what do I do next?" answer is obvious at a glance (<2s); competing co-equal CTAs are collapsed to one primary + quieter alternates.

**P-UX-10. Consistency with platform & product conventions (Jakob's Law — external consistency; Nielsen heuristic #4, consistency & standards). Match the conventions users already learned — inside the product (internal) and across the platform/web (external). Deviate only with a clear, user-worth-it reason.**
New. *Why:* "users spend most of their time on *other* products" (Jakob's Law), so they arrive with expectations: a logo links home, a cart sits top-right, the primary dialog button is on the platform's conventional side, underline means link, ⌘K opens search. Honoring these means zero re-learning; breaking them for novelty charges every user a small tax. Internal consistency — one word per concept, one component per job, the same thing in the same place — compounds the benefit inside your product and is the cheapest learnability win there is.
*Check:* standard elements behave as users expect (nav, links, icons, form controls, platform-correct dialog button order); terminology and component usage are consistent across the product (one word per concept, one component per job); any deliberate break from convention has a stated, user-worth-it justification (record it in `personality.md`, the same way visual deviations are declared).

## Composition defaults
- **A defaults kit:** every optional field pre-filled with the safe/common/reversible value (P-UX-03); known values carried forward, never re-asked (P-UX-01).
- **Disclosure:** common-case controls in the primary view, advanced one obvious step away, ≤2 levels (P-UX-04).
- **Recoverability over interruption:** an undo-toast pattern as the default for reversible actions; autosave/version history; hard confirmation only for irreversible high-stakes actions (P-UX-06).
- **Prevention-first inputs:** constrained pickers, disabled-until-valid, forgiving-then-normalized formats; remaining errors carry F69 copy and P-AY-07 wiring (P-UX-05).
- **A status discipline:** feedback within the 0.1/1/10s budget, core actions targeted <400ms, measured as round-trip + render (P-UX-07); skeletons that match layout, optimistic UI only where safe (P-UX-08).
- **One primary action** per screen, hierarchy stepping down from it (P-UX-09); **conventional** placements and terminology throughout (P-UX-10).

## Forbidden moves
- **A confirmation dialog on a reversible action** — tax on every action, protection for none; use undo (P-UX-06).
- **A spinner for a multi-second full-page load** where a layout-matching skeleton belongs (P-UX-08).
- **Optimistic UI on a payment or destructive action** — rollback is disorienting or impossible (P-UX-08).
- **A flat mega-menu / wall of equal options** where grouping or staging would halve the decision (P-UX-02; Hick).
- **Re-asking a value the user already gave** — or requiring them to remember it across steps (P-UX-01).
- **Hiding a common-case control behind disclosure**, or disclosure deeper than 2 levels (P-UX-04).
- **Two or more co-equal primary CTAs** on one screen — nothing is primary then (P-UX-09).
- **Breaking a strong platform convention for novelty** with no user-worth-it reason (P-UX-10).
- **An action with no status feedback** — the user can't tell if it registered, so they double-submit (P-UX-07).
- **A "good default" that serves the business over the user** — that's preselection, a deceptive pattern (P-UX-03 → P-EN-11).
