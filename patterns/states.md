# Pattern: State handling (the unhappy paths)

**Inherits:** all of `fundamentals.md` unless overridden below — especially F33 (every data view ships loading/empty/error/populated), F69 (error copy = problem + fix), F73 (tone matches the moment), F32 (interactive states), F34 (focus rings).
**Cite as:** `P-ST-<nn>`.

> **Cross-cutting pattern, NOT a surface archetype.** Like motion (`patterns/motion.md`) and containers (`patterns/containers.md`), this is a layer every surface reaches for. F33 *names* the four data states; **this file specifies the unhappy three** — loading, error, and the non-first-run empties — plus the states F33 doesn't enumerate at all: partial failure, slow/pending, offline, stale-while-revalidate, optimistic + rollback, and success/confirmation. It owns the **transitions between states and the decisions inside each** (skeleton vs spinner, inline vs section vs page error, optimistic vs pending). It does **not** re-own the *first-run / 404 / 403 / no-results* full-screen moments — those are `patterns/empty-states.md` (P-ES), specified there in full. This file points at P-ES for those and covers everything else; the boundary is **P-ST = the in-flight and in-failure mechanics, P-ES = the standing empty/error destinations.**

## Surface intent
The happy path is the demo; the state machine is the product. A surface that only renders its populated state is unfinished by definition (F33, AP19) — and the tell isn't usually a *missing* state, it's a **wrong, mis-scoped, or conflated** one: a spinner where a skeleton belonged, a full-page error blanking a page where one widget failed, a raw stack trace where plain copy belonged, a list that *failed to load* rendering the same "Nothing here yet" as a list that's *genuinely empty*. The job of this pattern is to make every state **truthful** (it says what's actually true — loading ≠ empty ≠ error ≠ offline), **correctly scoped** (the failure stays the size of what failed), and **recoverable** (every dead-stop hands over a next move). Which state-treatment is right is *contextual* — it falls out of the surface, the expected wait, and what failed — so this pattern is decision guidance (when X, use Y), never one rigid recipe.

## The first distinction — empty ≠ error ≠ loading (the one that's most often wrong)
A region with no data can be in three completely different truths, and conflating them is the single most common state bug:
- **Loading** — data is *in flight*; we don't yet know if it's empty, full, or broken. Show motion/skeleton, never an empty message.
- **Empty** — the fetch *succeeded* and returned zero rows. This is P-ES territory (first-run vs filtered-no-results — they're different too). Says "nothing here (yet / matching)", offers create-or-clear.
- **Error** — the fetch *failed*; we have **no idea** if there's data. Says "couldn't load this", offers **retry**. Never "Nothing here yet" — that asserts a fact (it's empty) the failed request can't support.
Rendering an empty-state for a failed load is a lie that sends the user to "create one" when their data is sitting safe on a server that just timed out. Decide which truth you're in *before* picking a treatment.

## Density band
**Inherit the host surface's band — a state treatment never changes the density of what it replaces.** A skeleton mirrors the populated layout's geometry exactly (P-ST-02), so a compact table's skeleton is compact rows, a spacious dashboard card's skeleton is a spacious block. Inline/section errors live at the host's field/region rhythm. The only state with its *own* band is the **full-page** error/404/offline (P-ES sparse band — centered cluster). Texture: none on in-flight/in-region states (they're transient product chrome); the sparse full-page moments may carry one device per P-ES-09.

## Calibrations

**P-ST-01. Pick the loading indicator by expected wait AND whether the layout is known — skeleton when the layout is known and the wait is ~300ms–a few seconds; spinner when the layout is unknown, the region is tiny, or the wait is very short/indeterminate; nothing (be optimistic) under ~100–300ms.**
Refines: F33, P-MT-07. *Why:* the indicator is a promise about what's coming — a skeleton promises "*this specific layout* is arriving" and prevents the reflow-jump a spinner-then-content causes; a spinner only promises "something is happening" and is right when you genuinely can't predict the shape (a freshly-typed search, a route whose content is unknown) or the region is too small to skeleton (a button, a 24px avatar). A skeleton for a 150ms toggle is overkill that flashes; a spinner for a known dashboard is a missed chance to show the layout. Reference study of real, public, shipped products: Neon (skeleton *table rows* matching its compute columns), Vercel Speed Insights (skeleton score-ring + chart blocks in the real card positions), Quicken (skeleton sidebar + two content cards in their final slots), Frame (skeleton main + right panel) — all skeleton **because the layout was known**; Threads/Canva used a bare spinner where the content shape wasn't predetermined (`evidence/states.md`).

**P-ST-02. A skeleton MIRRORS the final layout — same column structure, same card slots, same approximate text-line widths — so content arrives in place with zero reflow. Never a generic centered spinner standing in for a layout you already know.**
Refines: F33, P-ST-01. *Why:* the skeleton's entire value over a spinner is *spatial* — it reserves the exact geometry so the populated state doesn't shove the page around on arrival (the layout-shift the user feels as jank). A skeleton that's three grey bars where a 6-column table is coming is barely better than a spinner. Vercel/Neon/Quicken/Frame each laid their skeleton out as a desaturated tracing of the real screen, down to row counts and the score-ring's circle (`evidence/states.md`). Shimmer (1000–1400ms ease-std sweep, P-MT-07) signals "working"; reduced-motion drops the shimmer to a static block (P-MT-10).

**P-ST-03. Error scope matches what failed — inline (one field), section/region (one widget, list, or card), or full-page (the whole route/app). Never blow a region failure up to a full-page blank, and never bury a route-level failure inside a card.**
Refines: F33, P-ES-10. *Why:* scope is the tell that the failure was *reasoned*, not stamped. One failed dashboard card should retry *itself* while the other eleven widgets, the sidebar, and the nav stay live and usable — wrapping the whole app in one error boundary so a single widget's 500 blanks the page is the resilient-UI anti-pattern (wrap *risky regions*, not the whole app — `evidence/states.md`). Reference: Remote's import wizard kept its full step-chrome (Upload ✓ · Map fields ✓ · Review ✓ · Confirm) intact while only the *content region* showed "Sorry, something went wrong on our end — Retry"; a full-page error there would have destroyed the user's progress context. Conversely a true route-level failure (the page itself can't load) earns the whole viewport (Threads, Skiff, PayPal).

**P-ST-04. A field-level error sits AT the field it belongs to — red label + red border + a one-line message directly below naming the problem AND the fix (F69) — and only the offending field reddens. A form-level error (whole-submit failed, credentials wrong) sits in a section banner above the form. Never raise a single-field problem to a page-wide banner, or bury a whole-form failure inside one arbitrary field.**
Refines: F69, F32, P-F. *Why:* error proximity *is* the recovery affordance — the user fixes what's marked, where it's marked. Reference study: The New Yorker reddened **only** the invalid "Credit card number" field ("Your card number is invalid.") leaving valid fields untouched; Melio/Substack/Plaid/Aboard each put the message directly under the specific field with a red icon/border; Linktree used a *section banner* ("Password must be at least 8 characters") above the field set for a form-level rule (`evidence/states.md`). The scope of the red matches the scope of the problem — exactly P-ST-03 applied to forms.

**P-ST-05. Every genuine error is calm, factual, and plain-language (F69/F73), and ENDS in a retry — defers to P-ES-03 for the full-page error and the no-jokes-no-codes rule; this rule adds the *scoped* (inline/section/widget) cases P-ES doesn't cover.** A failed widget shows a short cause + a `Retry` on the widget; a failed submit shows the section banner + lets the user re-submit; the retry is the primary affordance every time.
Refines: F69, F73, P-ES-03. *Why:* P-ES-03 nailed the *full-page* error (Zoom/Udemy stayed flat and factual, retry primary); the same discipline governs the smaller scopes, which P-ES doesn't enumerate. A reference code is allowed as **fine print, never the headline** — PayPal's "Something went wrong / This happens sometimes. Trying again may help fix the problem / Debug ID: f8482509254bd / Retry" is the model: human cause line, retry primary, machine ID demoted to support fine-print (`evidence/states.md`). Jokiness stays out of genuine errors (F73); a sad mascot is tolerable on a light/transient failure, never on a payment or data-loss failure.

**P-ST-06. Partial failure is its own state: when some data loads and some fails, show what succeeded and scope the failure to the part that broke — a per-section/per-row error with its own retry — rather than failing the whole view or silently hiding the gap.** A dashboard with one dead widget renders the other eleven and marks the twelfth "Couldn't load — Retry"; a list where page 2 fails keeps page 1 and shows a retry at the boundary.
New. *Why:* the all-or-nothing reflex (one fetch fails → blank the screen) throws away data the user could already be using, and silently dropping the failed part is worse — it lies by omission (the user thinks they're seeing everything). Sometimes a *partial rollback* — keep an optimistic change visible but visibly marked "failed, retry" — is more user-friendly than a hard revert (`evidence/states.md`). Partial failure is the realistic default for any surface that fans out into multiple independent fetches; designing only "all loaded" and "all failed" is the AP19 happy-path tell at the data-orchestration layer.

**P-ST-07. Optimistic UI for fast, reversible, low-stakes mutations — apply the change instantly, reconcile on the server response, and ROLL BACK visibly with a non-blocking error toast if it fails. Do NOT use it for slow, high-stakes, or hard-to-reverse actions (payments, deletes, submissions) — those show a pending state and wait for confirmation.**
Refines: P-MT-07. *Why:* an optimistic toggle/like/reorder/rename feels native because the UI tracks the user's intent with zero latency — but only when a failure can be undone cheaply and the stakes of a brief wrong-state are low. The discipline that makes it safe: each mutation carries a request identity so only the latest commits or rolls back and stale responses are ignored, and a failed mutation reverts the snapshot *and* tells the user (a quiet toast, not a silent revert that leaves them thinking it worked) (`evidence/states.md`). Using optimism on a payment is the dangerous version — show pending, confirm for real (pairs with P-CK pending rules). The line is **reversible-and-cheap ⇒ optimistic; consequential-or-slow ⇒ pending-then-confirm.**

**P-ST-08. A button/action that triggers async work shows its OWN pending state — disabled + spinner-in-place + a verb shift ("Save" → "Saving…") — and the result lands as a toast or inline confirmation, not a full-page reload. The trigger, not the page, owns the wait.**
Refines: F32, F68, P-MT-06. *Why:* localizing the wait to the control that caused it keeps the rest of the surface live and tells the user exactly which action is in flight; blanking the whole page for one button's save is the over-scoped version of P-ST-03. Reference: June showed a "Saved successfully" toast while the page kept working, Sora "Saved username", Maze "Confirmed!", Air/Lovable confirmation toasts — the confirmation is a brief top/edge toast decoupled from any page reload (`evidence/states.md`). The spinner sits *in the button* (P-MT-06 press timing); the label's verb shift is the textual half of the same feedback.

**P-ST-09. Background refetch / stale-while-revalidate keeps the stale data VISIBLE and interactive while fresh data loads, with a quiet refreshing affordance — never blank-then-skeleton a screen that already has content. On arrival, replace in place; never show data you know is stale once you have fresh.**
New (ties P-MT-07, P-ST-02). *Why:* re-skeletoning an already-populated screen on every revalidation is a jarring regression — the user had something to read and you took it away to show grey bars. The right feel is "what you see is still here, and it's quietly updating" — a subtle top-bar progress sliver or a small spinner by the refresh control, content fully usable underneath (Canva dimmed-overlay-plus-spinner over its still-laid-out gallery is a mild version; the cleaner pattern is no dim at all, just a refresh indicator). The contract: stale-while-revalidate shows stale *only until* fresh arrives, then swaps in place — it must never *persist* known-stale data (`evidence/states.md`).

**P-ST-10. Offline / connection-lost is a distinct, reassuring, transient state (not a hard error): a persistent but unobtrusive banner ("You're offline — we'll retry") that auto-retries and auto-dismisses on reconnect, while keeping already-loaded content usable. Full-screen offline messaging is for when nothing is usable. Defers to P-ES-06 for the full-page offline moment.**
Refines: P-ES-06, F73. *Why:* a dropped connection is temporary and not the user's fault (F73 allows warmth here, unlike a genuine error); the tone is "we've got it, hang on", and the priority is *not* yanking away content the user can still read offline. A thin reconnecting banner that resolves itself beats a modal that blocks a user who was mid-read. P-ES-06 owns the case where the app genuinely can't function offline (full-screen); this rule owns the *degraded-but-usable* in-app banner case.

**P-ST-11. Success/confirmation is proportional to the action's weight: a quiet auto-dismissing toast for routine reversible actions (save, copy, send), an inline confirmation for in-context results, and a full success SCREEN only for the end of a significant flow (signup complete, payment done, order placed). Don't celebrate a field-save with a full-page interstitial, and don't bury a completed payment in a 2-second toast.**
Refines: F73, F68, P-MT-02. *Why:* over-celebrating routine actions trains the user to ignore confirmations (the boy-who-cried-toast), and under-celebrating a milestone leaves them unsure it worked (did my payment go through?). Reference: the routine saves were all brief toasts (June, Sora, Maze, Contra, Air, Lovable — `evidence/states.md`); a checkout/onboarding *completion* earns a real screen (P-CK / P-ES first-run lineage). Match the ceremony to the stakes.

**P-ST-12. Every async/state change is announced to assistive tech and respects reduced-motion (Tier-1, never yields). Toasts and inline status use `aria-live="polite"` (errors `assertive`); a loading region marks `aria-busy`; the skeleton's shimmer, the spinner's spin, and any state-transition motion all have a reduced-motion fallback (P-MT-10/F31).** A screen-reader user must learn "loading", "loaded", "saved", "failed — retry" without seeing the visual cue.
Refines: F34, F31, P-MT-10. *Why:* state changes are *exactly* the information sighted users get from motion and color — if the only signal that a save failed is a red toast that fades, a screen-reader or motion-sensitive user is told nothing. `aria-live` carries the state change to the AT; reduced-motion turns the shimmer/spin into a static indicator that still conveys "working" (F33's loading state must survive with no movement, the way an empty state must survive with no illustration). A state machine with no a11y announcement is unfinished the same way a data view with no empty state is (F33).

## Composition defaults
- **Decide the truth first** — loading / empty / error / offline / stale are five different facts; never let one render as another (the opening distinction). Empty further splits first-run vs no-results (P-ES).
- **Loading**: skeleton mirroring the layout when the shape is known + wait is ~300ms+ (P-ST-01/02); spinner when shape unknown / region tiny / very short; nothing (optimistic) under ~100–300ms. Shimmer per P-MT-07, reduced-motion static.
- **Error, by scope** (P-ST-03/04/05): field → red field + message below (problem + fix); section/form → banner above the form; widget/region → in-card cause + `Retry`; route/app → full-page (defer to P-ES-03/04). Plain copy, retry primary, machine code as fine-print only.
- **Partial failure** (P-ST-06): render what loaded, scope the failure + its retry to the broken part; never blank everything or silently hide the gap.
- **Mutations**: reversible-cheap → optimistic + visible rollback toast (P-ST-07); consequential-slow → button pending state + confirmation (P-ST-08); the trigger owns the wait, not the page.
- **Refetch** (P-ST-09): keep stale content live + quiet refresh affordance; swap in place; never re-skeleton a populated screen, never persist known-stale data.
- **Offline** (P-ST-10): unobtrusive auto-retrying banner, content stays usable; full-screen only when nothing works (P-ES-06).
- **Success** (P-ST-11): toast for routine, inline for in-context, full screen only for milestone completion.
- **A11y (all)** (P-ST-12): `aria-live` for async status, `aria-busy` for loading regions, reduced-motion fallback on every animated indicator.

## Forbidden moves
- **An empty-state rendered for a failed load** — "Nothing here yet / Create one" where the fetch actually *errored* (the truth-confusion at the top of this pattern; it lies about whether data exists).
- **A spinner where a skeleton belonged** — a known layout (dashboard, table, detail) loading behind a bare centered spinner, then reflow-jumping when content lands (P-ST-01/02).
- **A region failure blown up to a full-page blank** — one dead widget shouldn't blank the route; one failed save shouldn't reload the app (P-ST-03; wrap risky *regions*, not the whole app).
- **A single-field error raised to a page banner** (or a whole-form failure buried in one arbitrary field) — error scope must match problem scope (P-ST-04).
- **Raw codes / stack traces / system vocabulary shown as the error** — "Error 422", "null", "fetch failed", a DB field name (F69/F73; a reference ID is fine-print only, à la PayPal's Debug ID — P-ST-05).
- **Jokiness in a genuine error** — calm and factual; warmth is for 404/offline/empty, not a payment or data-loss failure (F73; P-ES-03).
- **All-or-nothing on a multi-fetch surface** — no partial-failure design, so one fetch failing blanks the screen *or* silently vanishes (P-ST-06).
- **Optimistic UI on a consequential/irreversible action** — applying a payment/delete optimistically, or rolling back *silently* so the user thinks it worked (P-ST-07).
- **The whole page blanking for one button's async work** instead of the trigger showing its own pending state (P-ST-08).
- **Re-skeletoning a screen that already has content** on background refetch, or persisting data you *know* is stale once fresh has arrived (P-ST-09).
- **A blocking full-screen offline wall** over content the user could still read, for a transient connection drop (P-ST-10).
- **A full-page success interstitial for a routine save** (or a milestone completion reduced to a 2-second toast) — mismatched ceremony (P-ST-11).
- **Any state change with no `aria-live` announcement, or any indicator with no reduced-motion fallback** — Tier-1 unfinished (P-ST-12; F31/F34).
- **Only the happy path** — the meta-tell (AP19): a beautiful populated state and none of the above designed at all.
