# Pattern: Engagement (motivation, habit & the ethical line)

**Inherits:** all of `fundamentals.md`; pairs with `patterns/usability.md` (P-UX — the ease layer) and `patterns/empty-states.md` (P-ES — first-run). Engagement sits *on top of* usability: a product no one can use can't form a habit, and a habit built on a frustrating tool is a trap.
**Cite as:** `P-EN-<nn>`.

> **Cross-cutting pattern — the behavioural layer, with the ethics baked in.** This is net-new ground for Lookbook: motivation, habit formation, retention, and — load-bearing — **the line between healthy engagement and manipulation.** Every recommended mechanic here is tagged **`[RECOMMENDED]`** (and several **`[RECOMMENDED — bounded]`**, healthy only inside a constraint); the deceptive ones are tagged **`[FORBIDDEN]`**. The frame for the whole file is Tristan Harris / Center for Humane Technology's distinction: optimize for **time *well* spent** (did the user accomplish what they came for and leave satisfied?), not **time *on* site** (minutes maximized regardless of outcome). The two align for tools the user *wants* to be good at (Duolingo, a fitness app, a great editor) and diverge sharply for attention-harvesting feeds. **Scope note:** many surfaces Lookbook serves — government, admin, internal, transactional (DVLA-style) — need only the **ethical floor** (P-EN-10 + P-EN-11); they should *not* grow streaks or variable rewards. Reach for the habit mechanics (P-EN-01..09) only when the product genuinely benefits from the user returning, and even then pass every one through P-EN-10 first.
>
> **Production-scope (read this before the `[FORBIDDEN]` rules constrain your ideation).** These rules forbid *deceiving a real user in a shipped product* — **not** placeholder data in a mockup, prototype, or design exploration. A fabricated "1,200 viewing" or "only 2 left!" *shipped to real users* is a dark pattern; the **same number as placeholder** in a prototype that will later be wired to real data is scaffolding, not deception — exactly like realistic sample names, seeded rows, or a stub API, which Lookbook *encourages* for design fidelity. The violation is **intent to deceive a real end user, judged at ship time** — not the presence of illustrative data in an artifact. So ideate freely with realistic counts/ratings/activity; the one discipline is to **flag placeholder social-proof/scarcity as placeholder** (a TODO, a stub marker, obviously-fake values) so it can't be silently shipped as-is and mistaken for real — it must become true data or be removed before production. (This mirrors §11's "fake data that screams fake" guidance for *quality*; here the concern is *honesty to real users*, and both resolve the same way: real data before ship.)

## Surface intent
Engagement design answers: **why does a user come back, and is that return in *their* interest or only the business's?** The behavioural science is neutral machinery — variable reward, loss aversion, progress, social proof, open loops all *work*, which is exactly why they're dangerous. The same progress bar that motivates a user to finish *their* course can be manufactured to extract a return visit that serves no one but the metric. So this pattern is two things at once: a catalogue of mechanics that genuinely help users build habits *they want*, and a hard boundary — Harry Brignull's deceptive-patterns taxonomy plus the regulatory reality (FTC and EU enforcement now carry nine-figure penalties) — past which a mechanic is not "aggressive growth," it's a defect. The test that governs all of it: **would the user still choose this if they fully understood it?**

## Density band
**No density of its own.** Engagement mechanics are about *timing and motivation*, not pixels. The relevant axis is not compact-vs-spacious but **needed-vs-not**: a transactional/admin surface needs only P-EN-10/11; a learning, fitness, creation, or community product can justify the full set — always gated by the five tests.

## Calibrations

**P-EN-01. `[RECOMMENDED]` Activation to first-value — get the user to the "aha moment" fast; show value before asking for setup; do-don't-tell. The empty state is the first onboarding step, not a dead end.**
Bridges `patterns/empty-states.md` (P-ES-01). *Why:* retention is decided at the *start* — a user who never reaches first value never forms a habit, however good the loop. Time-to-value (TTV) is the metric: the gap between arrival and the first moment the product visibly pays off. Slack auto-populates a new workspace with starter channels and next-step prompts instead of a blank void; Notion's onboarding morphs the workspace preview in real time so the user sees their result before committing; Superhuman onboards in a live session that lands the user at inbox-zero in one sitting. "Do, don't tell": users retain what they *accomplish* far better than what a tooltip tour *narrates* (the specific retention multiple is folklore — treat as directional, not measured; see `evidence/engagement.md`).
*Check:* the first session reaches a visible payoff before demanding configuration; empty states show a worked example / starter content / one clear next action (P-ES-01), never a blank canvas; onboarding lets the user *do* the core action, not watch a tour; TTV is something the team can name and is trending down.

**P-EN-02. `[RECOMMENDED]` Raise *ability* before motivation (BJ Fogg, B=MAP — Behaviour = Motivation × Ability × Prompt). When a behaviour isn't happening, reduce its friction first; reach for motivational pressure last. This is the anti-dark-pattern north star.**
New. *Why:* Fogg's model says a behaviour fires only when motivation, ability, and a prompt converge. The load-bearing insight: **raising ability (making the action easier) is more effective and more sustainable than raising motivation** — motivation is expensive and fluctuates, so behaviours that depend on it lapse the moment it dips. This is the exact *opposite* of the dark-pattern reflex (guilt, urgency, fear). Google's "did you mean?" raises ability (corrects the query for you); Duolingo framing a lesson as "just 5 minutes" lowers the ability barrier. The common mistake is misdiagnosing the bottleneck — pushing urgency/stre<x>aks</x> when the real blocker is that the task is too many steps.
*Check:* when a desired behaviour is under-happening, the first lever pulled is *friction reduction* (fewer steps, smarter defaults P-UX-03, better disclosure P-UX-04), not emotional pressure; motivational mechanics (P-EN-03/04) are layered on top of an already-easy action, never used to paper over a hard one.

**P-EN-03. `[RECOMMENDED]` Progress toward *user-set* goals (Goal-Gradient effect + endowed progress — Kivetz, Urminsky & Zheng 2006). Show honest proximity to a goal the user actually wants; an illusory head-start accelerates effort.**
New. *Why:* people accelerate as they near a goal, and a head-start compounds it — Kivetz's classic study: a 12-stamp card with 2 pre-stamped (i.e. a "10-purchase" card framed as already 2 in) was completed ~33% faster than a plain 10-stamp card, same real distance. LinkedIn's profile-strength meter and Notion's getting-started checklist ride this. **The ethical line:** RECOMMENDED when the goal is one the *user* set (finish a course, complete a profile *they* want complete, fill in *their* data). It slides toward FORBIDDEN when the "progress" is manufactured to drive *platform* metrics — e.g. "your account is 40% complete" where the missing 60% is optional fields that benefit only the business, or a progress bar whose proximity is dishonest (step 4 is 80% of the real work).
*Check:* the tracked goal is the user's, not the platform's; progress reflects *real* proximity (no fake "almost there"); completion delivers something the user wanted; no manufactured-incompleteness used purely to pull return visits (cross-ref P-EN-11, P-EN-05).

**P-EN-04. `[RECOMMENDED — bounded]` Streaks tied to *real activity*, with an escape valve (loss aversion — Kahneman & Tversky, Prospect Theory). A streak ties accumulated effort to the threat of loss, which motivates return more than the equivalent gain — but only when the streaked activity is genuinely the user's goal, and only with a forgiveness mechanism.**
New. *Why:* losses loom ~2× larger than equivalent gains, so "don't break your 30-day streak" pulls harder than "earn a badge." Duolingo's streak is a documented retention driver, and its **streak-freeze** (a built-in forgiveness that protects an at-risk streak) measurably reduces churn — crucially, it's a *user-empowering escape valve*, not a monetization trap. **The bound (where it turns dark):** FORBIDDEN when the streak requires *empty* activity to maintain (Snapchat-style streaks kept alive by sending any message — pressure fully divorced from meaningful use), when streak-anxiety becomes the *primary* motivator over the actual value, or when there's no mercy mechanism so a single miss punishes hard. A streak must reward a habit the user *wants* to have.
*Check:* the streaked action is the user's real goal (a lesson completed, not a content-free ping); a forgiveness mechanism exists (freeze/grace/repair); breaking a streak is disappointing, not punishing; the streak is not the *only* reason to return.

**P-EN-05. `[RECOMMENDED]` Open loops for the user's *own* tasks (Zeigarnik effect). Unfinished tasks the user cares about persist in memory and pull them back — surface their in-progress state honestly (a draft, a half-done checklist, an incomplete profile *they* want done).**
New. *Why:* Zeigarnik (1927): incomplete tasks occupy working memory more than completed ones — the brain keeps an "open loop." A visible in-progress state (a saved draft, a partially-filled setup the user initiated, a checklist with two of five done) leverages this to bring users back to *finish their own work*. **The line:** RECOMMENDED when the open loop is the user's genuine task; it tips toward FORBIDDEN (shared with P-EN-03) when teams *manufacture* incompleteness — flagging a profile "40% complete" where the missing fields exist only to serve the platform — to fabricate a return trigger with no user benefit.
*Check:* the surfaced incomplete state is a task the user actually started or wants done; finishing it benefits the user; no artificial incompleteness invented solely to drive return visits.

**P-EN-06. `[RECOMMENDED — bounded]` Variable reward only when the reward has *real value* (intermittent reinforcement — Skinner; applied via Eyal's Hook Model). Unpredictable rewards reinforce behaviour more strongly than fixed ones — legitimate when each reward genuinely benefits the user, manipulative when engineered for compulsion with no payoff.**
New. *Why:* variable-ratio schedules produce the most persistent behaviour, because anticipation itself drives dopamine. Healthy uses deliver real, if unpredictable, value: Spotify's Discover Weekly (the *quality* of discovery varies, but it's genuinely useful), a surprise of *useful* content. **The bound (the sharpest line in this file):** FORBIDDEN when the "reward" is pure dopamine with no real-world value — the infinite-scroll feed tuned to maximize dwell time beyond the user's intent, the gambling-adjacent loop. The honest tell: variable reward + the user's stated goal *exceeded against their will* (they came to "check what's new" and leave an hour later) = exploitation. The Hook Model is *neutral machinery*; Eyal's own pre-condition (the "Manipulation Matrix": build it only if it materially improves the user's life AND you'd use it yourself) is the gate growth teams routinely skip.
*Check:* each variable reward delivers something the user would call valuable in hindsight; the loop respects the user's *expressed* intent (a stopping point, not engineered bottomlessness); it passes the Manipulation Matrix (improves the user's life + you'd use it yourself); if the only thing varying is dwell-time-maximizing content, it's forbidden.

**P-EN-07. `[RECOMMENDED — bounded]` Accurate social proof only (Cialdini — *Influence*). Real ratings, counts, and activity reduce decision uncertainty; fabricated counts, false urgency, and manufactured scarcity are deception.**
New. *Why:* in uncertainty people follow others' behaviour — Airbnb's real review counts and ratings reduce booking anxiety; reciprocity (Dropbox's "give a friend space, get space") drives honest referral growth. **The bound:** FORBIDDEN — and increasingly *illegal* — when the social proof is fake: invented "1,200 people are viewing this," countdown timers that reset on reload, "only 2 left!" that's untrue, fabricated review counts. These are deceptive patterns under Brignull's taxonomy and active FTC enforcement targets.
*Check (at ship time):* every count, rating, "X viewing", scarcity, and urgency signal shown to *real users in production* is true and current; no reset-on-reload timers, no invented viewer counts, no fake stock pressure; social proof is representative, not cherry-picked into a lie (cross-ref P-EN-11). *Placeholder counts in a mockup/prototype are fine and encouraged for fidelity — see the production-scope note above; just flag them so they're replaced with real data before ship.*

**P-EN-08. `[RECOMMENDED — bounded]` Investment that creates *user-owned, portable* value (Hook Model, investment phase). The more a user puts in, the more they get out and the higher the switching cost — legitimate when the investment is genuinely theirs, manipulative when engineered purely to trap.**
New. *Why:* a user who imports data, builds a library, or creates content gets a better product *and* becomes less likely to leave — fine when the value is real and theirs: Notion templates, Figma component libraries, GitHub history all represent user-generated value that *happens* to create stickiness. **The line:** FORBIDDEN when lock-in is the *mechanism* rather than a side-effect — deliberately impeding data export, making key data non-portable, hiding the account-deletion path (Brignull's "roach motel" / obstruction). The test: is the switching cost a *consequence* of value the user owns, or a *barrier* the product built to hold them?
*Check:* investment produces value the user owns and can take with them (export, portability); the exit path (export, delete account, cancel) is as visible and easy as the entry path (P-EN-10 exit-path test); stickiness is a side-effect of real value, not an engineered cage.

**P-EN-09. `[RECOMMENDED — bounded]` Notifications as *signal*, permission-primed at the value moment. A notification should fire when the user needs a reminder and only then; ask for the permission when its value is evident, not on first launch.**
New. *Why:* an effective notification is a *signal* — it fires when motivation and ability are present and only the prompt is missing (Fogg). Slack defaults to notifying on direct @-mentions only — high signal, low noise, user expands by choice. Permission-priming (request access at the moment value is obvious, not cold on first open) raises opt-in dramatically and respects the user. **The bound:** FORBIDDEN when notifications become *nagging* — repeated prompts to re-enable, "come back" pings with no user intent behind them, re-engagement spam (Brignull's "nagging"). The trailing metric that exposes over-notification is the opt-out / uninstall rate.
*Check:* notifications map to genuine user need/relevance, not engagement quotas; permission is requested at a value moment, not first launch; declining is respected (no repeated re-asks); a user can tune notification types granularly; opt-out/mute is easy and honored.

**P-EN-10. The five manipulation tests — the gate EVERY engagement mechanic must pass. Apply before shipping any of P-EN-01..09.**
New (the operational gate; synthesizes Brignull + FTC enforcement pattern + Harris/CHT). Run all five:
1. **Informed-consent test** — would the user still engage if they *fully understood* the mechanism? (A streak for daily practice — yes. A streak engineered to trigger anxiety — no.)
2. **Whose-interest test** — does the *easy* path serve the user's stated goal, or only the business metric? (One-click signup but seven-step cancellation fails.)
3. **Cognitive-bias-direction test** — is a known bias (loss aversion, social proof, anchoring) being exploited *in the user's favour* or *against their expressed preference*?
4. **Transparency test** — if you published the exact mechanism ("we delay your send 30s so you can undo"), would users feel *helped* or *manipulated*?
5. **Exit-path test** — is the path *out* (cancel, export, delete, unsubscribe) as visible and easy as the path *in*?
*Check:* every engagement mechanic on the surface is run through all five and passes; any "no" is a redesign, not a launch. (These overlap the academic frameworks — Mathur et al. 2019 — and the regulators' working definitions.)

**P-EN-11. `[FORBIDDEN]` Deceptive ("dark") patterns — never ship these. They are not aggressive growth; they are defects, and increasingly *unlawful* (FTC + EU enforcement). (Harry Brignull's taxonomy, deceptive.design.)**
New. *Why:* these exploit cognitive biases *against* the user's interest, fail the P-EN-10 gate by construction, and now carry real legal and financial risk — not just reputational. The taxonomy to forbid by name:
- **Roach motel** — easy to get in, deliberately hard to get out (2-click signup, 7-step cancel).
- **Confirmshaming** — guilting the opt-out ("No thanks, I like paying full price").
- **Trick questions** — fine-print double-negatives on checkboxes ("Untick to not receive…").
- **Sneak into basket** — extras pre-added at checkout (insurance, donations).
- **Forced continuity** — free trial → silent paid conversion, cancellation buried.
- **Nagging** — repeated prompts after the user declined (cross-ref P-EN-09).
- **Obstruction** — making a desired action (cancel, export) artificially hard (cross-ref P-EN-08).
- **Preselection** — privacy-invasive or costly options pre-ticked (cross-ref P-UX-03).
- **Hidden costs** — true price concealed until late in checkout.
- **Fake urgency / scarcity / social proof** — reset-on-reload timers, invented viewer counts, untrue "only 2 left" (cross-ref P-EN-07).
**Regulatory reality (this is legal risk, not taste):** FTC — Epic Games **$245M** (2023, manipulative purchase UI), Amazon Prime (active case over signup/cancel dark patterns), Vonage **$100M** (cancellation barriers); EU — TikTok **€345M** (2023, steering children to privacy-invasive defaults), cookie-UI fines on Google/Meta/Amazon; the EU **Digital Services Act** and **Data Act** now expressly prohibit dark patterns; an ICPEN/GPEN sweep (2024) found **76%** of reviewed sites used ≥1.
*Check (production / ship time — mockups & prototypes are out of scope per the production-scope note above):* grep the *shipping* flow for each named pattern; the exit path equals the entry path; no pre-ticked options against user interest; no fine-print double-negatives; no fake urgency/scarcity/counts reaching real users; cancellation/export/deletion are first-class, not buried. Any instance *in production* is a blocker; the same artefact in a design exploration is not.

## Composition defaults
- **Floor first:** on *every* product, P-EN-10 (the five tests) and P-EN-11 (no deceptive patterns) apply unconditionally — they are the engagement equivalent of the contrast/a11y floor.
- **Habit mechanics are opt-in by product type:** activation/first-value (P-EN-01) is near-universal; streaks/variable-reward/social-proof (P-EN-04/06/07) belong only to products the user *wants* to build a habit with, and each ships only after passing the five tests.
- **Ability before motivation (P-EN-02)** is the default reflex: reduce friction (P-UX-03/04) before adding any motivational layer.
- **Honesty is the through-line:** real progress (P-EN-03), real activity behind streaks (P-EN-04), real social proof (P-EN-07), portable value (P-EN-08), signal-not-noise notifications (P-EN-09).
- **Exit parity everywhere:** the path out is always as easy as the path in (P-EN-10 test 5 / P-EN-11 roach-motel).

## Forbidden moves
- **Any pattern in the P-EN-11 taxonomy** — roach motel, confirmshaming, trick questions, sneak-into-basket, forced continuity, nagging, obstruction, preselection, hidden costs, fake urgency/scarcity/social-proof.
- **Variable reward with no real user value** — engagement engineered for compulsion / dwell-time, not benefit (P-EN-06).
- **Streaks on empty activity**, or with no forgiveness mechanism (P-EN-04).
- **Manufactured incompleteness** — fake "X% complete" to fabricate a return trigger (P-EN-03/05).
- **Cold notification-permission prompts on first launch**, or nagging re-asks after a decline (P-EN-09).
- **A default that serves the business over the user** (preselection — P-UX-03 / P-EN-11).
- **Shipping any engagement mechanic without running the five tests** (P-EN-10).
