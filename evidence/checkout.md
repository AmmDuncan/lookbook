# Evidence — Checkout / Billing (P-CO calibration)

Method: studied real web checkout / payment / order-review screens across e-commerce, subscription/SaaS billing, and food/meal-kit, read by **(a) craft to learn** and **(b) how the rules are applied** — where reality confirms a rule, calibrates a number, or breaks it. Checkout is the conversion-critical money surface; it inherits the form pattern (P-F) but raises the stakes — the user is about to enter a card, so trust, clarity, and a single unmistakable action matter more than anywhere else.

Screens (16 across 4 searches): Nike (payment-method + card), Apple (stepped "How do you want to pay?" + collapsed summary), HODINKEE (payment + right summary rail), Zoom (stepper checkout), Dollar Shave Club (single-column order summary + Complete Order), Blue Apron (2-col delivery/billing + summary rail + trust badges), adidas (2-col contact/address + "Your order" rail with discount + promo applied), Walmart (review with primary Pay-at-top sticky summary), Rows (payment-data modal), Tripadvisor (card + billing address, inline ✓ validation), ClassPass (single-column billing + Stripe marks + fine-print disclosure), Fresha (stepped billing details), Squarespace (5-step stepper + Review + summary rail + SSL mark), Pipedrive (subscription overview + payment-summary rail, charged-today vs recurring), Mailchimp (payment method + purchase-summary rail + Pay now). 2026-05-29.

## The dynamic-generation lesson
Checkout layout flexes on **how much the order carries and how many steps the purchase needs** — the same content-driven branch as P-F (entry vs settings) and P-DT (column count). A short cart (Dollar Shave Club, one item) is a single column with the summary inline; a standard cart (adidas, Blue Apron, Mailchimp) is two columns with a sticky order-summary rail; a long or compliance-heavy purchase (Squarespace domain, Zoom licensing, Apple) becomes a stepped flow with a collapsible summary so the total is never lost. The constants never flex: **every cost visible up front, ONE action that names the outcome and the amount, the action reachable without scrolling, and trust marks at the point of payment.** Getting the layout from the order's size — not stamping one template — is the proof the surface was reasoned from the purchase.

## Over-strict / wrong-rule catches
- **Apple's collapsed "Show Order Summary: S$140.25"** showed a summary can collapse on a stepped flow *as long as the total stays in the collapsed header* — the total is never hidden, only the line items. Calibrated P-CO-06 (stepped flows keep the total visible even when the breakdown collapses) rather than a naive "summary always fully expanded."
- **Walmart / Squarespace put the pay button at the TOP of the summary card**, not at the bottom of the form — softened a naive "primary bottom-right" (P-F-05) into P-CO-04's "reachable without scrolling": on a tall checkout the action belongs *with the total*, not at the end of a long field list.
- **Pipedrive / Mailchimp "charged today $0 vs $172.22/mo recurring"** proved a subscription checkout must make the *now* amount the headline and the recurring amount explicit — a single ambiguous "Total" here is the hidden-fee tell in disguise. Fed P-CO-02's charged-now-vs-recurring split.

## Calibrations applied to patterns/checkout.md
1. Layout → **2-col form + sticky order-summary rail default; single-page vs stepped contextual on item/step count** — the dynamic branch (P-CO-01).
2. Order summary → **line-item ledger, decimal-aligned, Total set apart, every cost up front, edit affordance, charged-now-vs-recurring split** (P-CO-02).
3. Payment fields → **card/expiry/CVV grouped, autofill-friendly, lock + accepted-cards + processor marks in the group, inline-blur validation, billing-same-as-shipping checkbox** (P-CO-03).
4. Primary action → **ONE button naming outcome + amount, reachable without scrolling (sticky summary / top-of-rail), secondary ghost** (P-CO-04).
5. Trust → **lock / accepted cards / encryption note clustered at the point of payment, functional not decorative** (P-CO-05).
6. Steps → **stepped for long flows, total stays visible even when breakdown collapses; single page for short carts** (P-CO-06).
7. States → **processing/disabled-while-submitting + calm payment-failure error path are mandatory, not optional** (P-CO-07).

### Over-strict / wrong-rule catches (Run 2)
- **P-CO-04 amount-in-button was effectively over-strict.** A large, *excellent* cluster (Zendesk, Squarespace, OpenAI, Synthesia, Square, Urban Outfitters, Apple) ships a verb-only outcome label because a set-apart Total sits immediately adjacent or the step precedes a Review. The rule's spirit — *no doubt about what happens and how much* — is satisfied by "outcome verb + adjacent unmissable Total," not only by literally printing the amount on the button. Calibrate P-CO-04 to make amount-in-button the *preferred* form, not the sole compliant one. (This is the most valuable catch of the run.)
- **"Estimated" totals are honest, not a hidden-fee tell.** Walmart "Estimated total", Unity "Est. Order total", Mixpanel "Prorated Total Due Today" show that when tax/shipping genuinely depend on a not-yet-entered address, an *"Estimated"* qualifier on a *still-fully-shown* ledger is correct — P-CO-02's "every cost up front" means *shown*, not *final-to-the-penny before address*. Worth a Check-line clarification so the rule isn't misread as "no estimates allowed."

### The express-pay gap (the run's main finding)
The single clearest gap vs. Run 1: **express-pay / digital-wallet buttons have no home in the pattern.** They are now a default expectation (≈70% of platform stores, measurable conversion lift) and have a stable, learnable placement grammar — wallet row *above* the card form with an "or pay with card" divider, OR as method tabs/radios alongside Card. This is genuinely *new surface behavior*, not a restatement of an existing rule, so per the refine-don't-add + battle-test discipline it is recorded as **NEW-RULE CANDIDATE P-CO-09**, folded provisionally into the P-CO-03/04 composition notes, and left for a baseline-vs-deepened battle test before any rule is added. Guest-checkout prominence is a weaker second candidate (strong external evidence, thin in-corpus visual proof).

### Net outcome
Refine-don't-add, healthy: **one soften-calibration adopted (P-CO-04 amount-in-button → preferred-not-mandatory)**, two Check-line clarifications (P-CO-02 "Estimated" qualifier; P-CO-07 processing state now has a live receipt), **zero new rules adopted**, **two NEW-RULE CANDIDATEs flagged for battle-test** (express-pay P-CO-09; guest-checkout prominence).
