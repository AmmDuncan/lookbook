Recipe 01

CRUD list #crud

Ingredients

  • page-header (compact)
  • filter-bar + active-filter chips
  • data-table w/ sortable headers + row selection
  • bulk action bar on selection
  • pagination
  • menu for per-row actions

Required states

  • Loading — table skeleton
  • Empty — first-use illustration + CTA
  • Empty — no search results (clear filters)
  • Error — full table failed (retry)
  • Error — row-level inline error
  • Success — toast after bulk action

Use when

Users browse, filter, and manage a homogeneous collection — projects, members, orders, invoices.
Mobile: sidebar → drawer behind a hamburger; table collapses to a card-per-row stack (title + 2–3 key fields + overflow menu); filter chips scroll horizontally.

Recipe 03

Create / edit form #form

Ingredients

  • page-header (compact)
  • sectioned form (meta + fields columns)
  • field + inline validation + helper
  • sticky footer with unsaved-changes counter
  • modal (confirmation) for the unsaved-changes guard
  • danger zone alert at the bottom

Required states

  • Pristine — no edits, footer disabled
  • Editing — footer shows "N unsaved changes"
  • Saving — primary button → "Saving…"
  • Success — toast + footer resets
  • Error — field-level + server-error banner
  • Leave-page guard — modal blocks navigation

Use when

User creates a new record OR edits an existing one with 3–15 fields across 2–5 logical sections.
Mobile: section meta column collapses above its fields (single column). Footer stays sticky. Unsaved-counter moves above the action row. Date pickers go full-width.

Recipe 04

Multi-step wizard #wizard

Ingredients

  • stepper bar — numbered, with active + completed
  • card — one per step
  • field — per-step form
  • btn · ghost "Back" · btn · primary "Next"
  • review summary list (final step before submit)
  • success screen (icon + heading + CTA)

Required states

  • Step 1..N — each step's form + validation
  • Review — read-only summary with "Edit" per group
  • Submitting — primary → "Creating…"
  • Submitted — full-screen success state
  • Error — submit failed, return to last step

Use when

First-time onboarding, big setup forms, or anything where a single page would be overwhelming and a clear sequence reduces cognitive load.
Mobile: stepper collapses to "Step 2 of 4" + thin progress bar. Next/Back become a sticky bottom bar.

Recipe 05

Settings page #settings

Ingredients

  • subnav — grouped, left rail
  • card — one per logical group
  • switch · checkbox · input · select
  • Per-card btn · primary "Save" OR global sticky footer
  • alert (danger) for the destructive zone

Required states

  • Default — nothing changed
  • Dirty card — Save button enabled
  • Saving — Save → "Saving…"
  • Saved — Save → ✓ → resets
  • Error — inline banner above the card

Use when

5+ unrelated preferences across distinct surfaces (profile, notifications, billing, security). Per-card save is preferable to a global save — reduces blast radius.
Mobile: subnav collapses to a horizontal scrolling tab strip or a dropdown. Each card spans full width.

Recipe 09

Checkout / billing #checkout

Ingredients

  • page-header (compact) with progress dots
  • Line-item list with stepper for quantity
  • Summary card with subtotal / tax / total
  • Payment fields with inline validation
  • btn · primary "Pay $X" — labels with the amount
  • Trust strip — SSL · 30-day refund · contact
Needs new component: card-input (PAN / CVC field with mask + brand detection). Use a placeholder Stripe/Lemon Elements mount in the meantime.

Required states

  • Empty cart — illustration + back to products
  • Field validation — declined / expired / wrong CVC
  • Processing — primary button → "Charging…"
  • Success / receipt — full page with print + email
  • Charge declined — actionable error + retry path

Use when

User commits money — checkout, plan upgrade, one-time purchase. Keep one screen if possible; never make the user re-enter data after an error.
Mobile: summary card moves below the form (or pinned bottom-sheet on tap). Payment fields are full-width. Total stays visible above the Pay button.

Recipe 12

Kanban / board #kanban

Ingredients

  • page-header (with tabs) for view switcher
  • Columns — header + count badge + add-card button
  • card per task (compact)
  • Drag affordance — grip dots on hover
  • filter-bar above
Needs new component: dnd-card (drag handle + drop-zone). Wrap any drag library; the visual contract is grip-on-hover + dashed insertion line + ghost preview.

Required states

  • Empty column — "Nothing here · add card" placeholder
  • Dragging — ghost card + dashed drop-zone target
  • Adding card — inline input at column top
  • Loading — skeleton cards in each column
  • Saving move — optimistic UI + revert on error

Use when

Workflow with discrete stages and a small-to-medium task volume — issue tracking, content pipelines, hiring funnels. Don't use beyond ~300 cards; switch to list/table.
Mobile: columns become a horizontal scroller, one column visible at a time + thumb-friendly scroll snap. Drag UX is rarely worth it on touch; offer tap-to-move instead.

How to use Recipes #howto

1

Pick the recipe

Match the task to a recipe. If two seem to fit, pick the one with fewer ingredients — restraint is the brand.

2

Compose from named parts

Use only the ingredients listed. If something's missing, surface a "needs new component" callout instead of improvising.

3

Ship every listed state

Empty, loading, error, success — required, not optional. A page without its states is a draft, not a feature.

4

Re-skin via tokens only

Every visual difference between projects comes from tokens.css. Never restyle a component inline.

The recipe is the contract. The tokens are the skin. Stay inside both and your work will feel like it belongs to Lookbook.
