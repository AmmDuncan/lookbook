Form field layout studies

One DVLA registration form, laid out sixteen ways. Unlike the other drill-downs, several variants here are wrong on purpose and marked so. Field layout is one of the few areas of interface design with real evidence behind it, so a neutral "pick the one you like" sheet would be a lie.

What this sheet is not. Form organisation — single-scroll, tabs, sidebar TOC, wizard, accordion — belongs to Long-Form Organization Studies. Where the form commits belongs to Action & Commit Placement Studies. This sheet is only about the fields.

How to read a verdict. Each variant carries ✓ Use, △ Depends, or ✗ Avoid, plus the source the verdict rests on. Where a rule has an exception, the exception gets its own frame rather than a footnote — that's the part people get wrong.

Axis A

Column structure

The most common form mistake, and the one with the least ambiguous answer. Two columns of unrelated fields force a zig-zag scan and measurably raise skipped fields.

Rule: one vertical column, labels above. The single exception: a genuinely compound field — parts of one answer, under one label. Baymard · NN/g Web Form Design · Adam Silver
A1Single column ✓ Use
One field per row, label above, in the order the answers are known. Nothing to scan for, nothing to skip.
one column · labels above · linear scan path

Axis B

Field width as a hint

Width is a silent instruction. A field sized for eight characters tells the user, before they type, roughly what belongs there — and a field sized wrong quietly misleads.

Rule: input width roughly proportional to the expected answer; flag mismatches beyond about 2×. A capped measure on the column is separate, and always worth having. NN/g Web Form Design
B1Everything full width, uncapped ✗ Avoid
The default when a form inherits its container. A two-character region code gets exactly the same width as a street address, so width carries no information at all — and the labels drift far from their inputs on wide screens.
width uniform · no signal · line length unbounded

Axis C

Where help and errors live

Help and errors are different channels doing different jobs. Help prevents the error; the error reports one that already happened. Collapsing them into one channel is the common failure.

Rule: format help renders under the label on load, muted, before anything is typed. Errors render at the field, on blur or after submit — never on the first keystroke of an untouched field. Adam Silver · Baymard inline validation · NN/g
C1Proactive hint under the label ✓ Use
The format is stated before the user types, muted and visually distinct from red. Most format errors never happen, which is cheaper than reporting them well.
hint present on load · muted ink · separate element from error

Axis D

One input, or several

The axis people get backwards. Splitting an answer across boxes is right in one specific case and wrong nearly everywhere else — and the two cases look identical from a distance.

Rule: split only a date the user already knows. Everything else — phone, card, reference — gets one input that accepts spaces, dashes and prefixes, then normalises. GOV.UK date patterns · web.dev payment & address · Baymard
D1Known date as three boxes ✓ Use
The user already knows this date, so typing beats picking. The hint uses a day above 12 and a month above 9 so the order is unambiguous without demanding leading zeros.
day 2 · month 2 · year 4 · numeric keyboard · works without JS

Lifting from this sheet: the ✓ frames compose — A3's compound row, B3's matched widths, C1's proactive hints and D4's single flexible input are the same form, and that combination is the house default. The ✗ frames exist so a reviewer can name what they are looking at, which is faster than re-deriving the rule.
