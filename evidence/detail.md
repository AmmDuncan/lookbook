# Evidence — Detail / Record / Profile (P-DT calibration)

Method: studied 11 real web detail/record/profile pages across five domains (CRM contact, auth user, product analytics user, e-commerce order, issue/ticket), read by **(a) craft to learn** and **(b) how the rules are applied** — where reality confirms a rule, calibrates a number, or breaks a rule (→ rule is wrong/too strict/needs scope). Reading reality is what catches the over-strict guess; the strongest calibrations below are rules that real screens *bent*.

Screens: Customer.io (Person/Activity), WorkOS (User profile), HubSpot (Contact — Overview + Activities), Amplitude (User profile/Activity), Apollo (Contact/Company insights), Salesforce (Contact), folk (Person/Notes), Shopify (Order — 3 views: timeline, summary, full record), Linear (Issue), Intercom (Help Desk ticket), Gorgias (ticket). 2026-05-29.

## The dynamic-generation lesson
Detail pages vary by **how much the record carries**: a CRM contact (HubSpot, Salesforce) is a hub of linked entities + a heavy activity stream → three columns; an order (Shopify) is a body (line items) + stable summary → two columns; a sparse issue (Linear) is a description + one timeline → near single column. The constant is the *reading order* — identity → facts → related → actions → history; the **column count and tabs-vs-stacked flex to the record's information mass.** A thin record in a three-column shell reads as broken (empty rails); a hub in one column buries its value. Getting this right is the proof the layout was reasoned from the content, not stamped from a template.

## Over-strict / wrong-rule catches (the strongest calibrations)
- **Customer.io's 8-tab strip** showed that "tabs are fine" needs a ceiling — tabs hiding a thin record is a tell. Fed P-DT-05's "tabs only when voluminous AND categorically distinct" + the forbidden 6+-tab move. (Mirrors the dashboard study catching "no tabs" as *too strict* — here the catch is the opposite: tabs need a *cap*.)
- **HubSpot `Tickets (0)` / `Payments (0)` blocks** proved related-record empties are *designed populated states with an add action*, not gaps to hide — extended F33 into sub-sections (P-DT-10).
- **Shopify's `Collect payment` next to the summary** (not in the header) showed the primary action belongs **near the thing it acts on**, not reflexively top-right — softened a naive "primary always top-right" into P-DT-08's contextual placement.

## Calibrations applied to patterns/detail.md
1. Identity header → **status pill adjacent to the title**, breadcrumb above, primary top-right (P-DT-01).
2. Layout → **contextual column count** (2-col content+rail default / 3-col CRM hub / single thin+mobile) — the dynamic branch (P-DT-03).
3. Summary/properties rail → **280–360px, 2–4 titled blocks, reflows below on mobile** (P-DT-04).
4. Sub-content → **tabs only when voluminous & distinct; stack ≤3 sections; cap tabs** (P-DT-05).
5. Related records → **count in heading + add/view-all; `(0)` renders a populated empty** (P-DT-06).
6. History → **vertical date-grouped timeline, never a raw table** (P-DT-07).
7. Actions → **one primary near its section; destructive in overflow menu** (P-DT-08).
8. Editing → **inline single-field edit, not a jump to a form page** (P-DT-09).
9. States → **per-region loading/empty/error, skeletons mirror layout** (P-DT-10).

## Run 2 — live-UI calibration, 2026-05-29

Method: a fresh reference study of real, public, shipped products, read **rule-by-rule** (VALIDATE / CALIBRATE / TOO-STRICT) to retest the P-DT calibrations against a *broader* spread than Run 1 — which skewed CRM-heavy. Deliberately widened to six domains so no single archetype set the numbers: CRM contact, e-commerce order, issue/ticket, support inbox, fintech transaction/invoice, and account/profile-settings. ~24 distinct products surveyed.

Screens (generic source, public product names): **CRM** — HubSpot (Contact: About-left / Activities / Intelligence; `Tickets (0)`/`Payments (0)` related blocks), Salesforce (Contact: 3-col About / activity timeline / Opportunities·Cases·Files), Attio (Record: Activity center + Record-details rail), Lightfield (Contact: activity + contact-details rail), Outseta (Person: activity + Information rail), Clay (Person: timeline + network/properties rail, map). **E-commerce order** — Shopify (Order #1001/#1002/#1003 across paid/pending/refunded/cancelled: line-items + summary + right rail of Notes/Customer/Shipping/Conversion/Fraud blocks + Timeline; multi-pill status row; "More actions" overflow), Walmart (order: progress-tracker + delivery rail), Selfridges & Urban Outfitters (storefront order: status strip + delivery + items), Deel (equipment order: 2-col card grid). **Issue/ticket** — Linear (issue: description + right properties rail + activity; sparse issue near-single-col), Intercom (Help Desk ticket: conversation + Details rail), Zendesk (ticket: left requester/assignee form + conversation), Gorgias & Plain (support ticket: conversation + customer/properties rail). **Fintech** — Stripe (payment: amount+`Succeeded` pill, Timeline, Payment breakdown, Details rail ~8 facts, "Add to block list" overflow), Wise (transaction: centered single-column card, vertical checkmark timeline, Updates/Details tabs), Mercury & Midday (invoice slideover: amount + status + activity + overflow Mark-as-paid/Delete), Airwallex (bill: doc-preview left + line-items/comments/timeline right), Harvest (invoice history: flat avatar audit list), Remote (contractor invoice: doc-preview + summary + timeline). **Profile/settings** — Apollo, Givingli, Brilliant, Acctual, Dovetail (section-Edit→reveal-fields-in-place), Airwallex personal (per-block Edit + Verified chips), Alan (profile with inline pencils + activation banner). 2026-05-29.

### Over-strict / wrong-rule catches (the value of this run)
- **Harvest's flat avatar audit list** and **Walmart's horizontal fulfilment stepper** are the strongest catches: P-DT-07's "history is a *vertical* timeline … never a raw table" reads as forbidding both, yet both are excellent, fit-for-purpose history devices. The real anti-pattern is a *raw data table of events*, not "anything that isn't a vertical connector." → soften P-DT-07.
- **The 3-col CRM left-identity-rail** (HubSpot/Salesforce/Attio put name+avatar+core fields atop the LEFT rail) is a layout the current pattern under-specifies — P-DT-01 + composition-defaults read as "identity is always a full-width header band," but the dominant CRM-hub shape heads the *left rail* with identity. → name it in P-DT-03.
- **Multi-pill status rows** (Shopify payment·fulfilment·lifecycle) gently break P-DT-01's singular "status pill" — orthogonal states legitimately warrant a small pill row beside the title. → scope-widen P-DT-01.
- **Section-level Edit toggle** on settings-style profiles is a second valid in-place-edit affordance P-DT-09 doesn't mention (it implies per-field pencil only). → scope-widen P-DT-09.

### Net
Zero new rules proposed (Refine-don't-add holds; Run 1 also added none). Four **scope/soften CALIBRATIONs** to existing rules (P-DT-01, P-DT-03, P-DT-07, P-DT-09), all loosening rigidity to match excellent real screens — no number tightening needed. One NEW-RULE-CANDIDATE flagged for battle-test (does not get added here): a "linear-lifecycle records use a horizontal stepper, branching/audit history uses a vertical timeline" device-selection rule — but it likely belongs folded into P-DT-07's softening rather than as its own rule. Proposed status text colors verified AA/AAA via `contrast.mjs` (green `#0b6b3a` 7.84:1; success/warn/danger on their tints all ≥6.3:1).
