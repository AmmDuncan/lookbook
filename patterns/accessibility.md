# Pattern: Accessibility (semantics — the non-color half of a11y)

**Inherits:** all of `fundamentals.md` unless overridden below — especially F15/F54/F55/F66 (contrast), F31 (reduced-motion), F34 (focus-visible), F52 (touch targets), F3/F5 (legibility). These are the **Tier-1, never-yields** floor (fundamentals.md precedence ladder).
**Cite as:** `P-AY-<nn>`.

> **Cross-cutting pattern — the semantic counterpart to the contrast gate.** Color/contrast is already operationalized as a *computed* gate (`scripts/contrast.mjs`, F15/F54/F55/F66) and SKILL.md mandates running it. This file operationalizes the **rest** of accessibility: the markup-level semantics that make an interface usable by keyboard, screen reader, and assistive tech — focus order, keyboard operability, roles/names/landmarks, error association, live regions, target size, skip-links. **Unlike every other pattern, this one is mostly DETERMINISTIC: there is a right and a wrong markup, not a contextual judgment.** So the `Check:` lines are auditable in the markup or with one keyboard/SR pass — not "look at the pixels." Load it on **every** surface that ships an interactive control, a form, an overlay, async content, or navigation chrome — i.e. nearly all of them. Reduced-motion lives in `patterns/motion.md` (P-MT-10/F31) — cross-referenced here, not duplicated. The four data states (loading/empty/error/populated) live in `patterns/empty-states.md` (P-ES) + F33 — this file owns how their *changes are announced*, not how they look.

## Surface intent
Accessibility-semantics answers one question for the ~1 in 5 users on a keyboard, a screen reader, a switch device, voice control, or a zoomed viewport: **can I perceive, reach, operate, and understand every part of this — without a mouse and without sight?** The failures are not subtle taste calls; they are binary breakages, and they are exactly the ones AI-built UI ships most: an icon-only button that announces nothing, a `<div onclick>` the keyboard can't reach, a focus ring deleted "because it looked ugly", an error message floating beside a field with no programmatic link, a modal that lets focus leak onto the frozen page behind it. The reference frame is **canon, not visual trend**: WCAG 2.2 AA success criteria, the WAI-ARIA Authoring Practices Guide (APG), the HTML and ARIA specs, and the precedence ladder's "a11y never yields." The first rule of ARIA applies throughout: *use a native HTML element before reaching for a role* — a real `<button>`, `<a>`, `<label>`, `<nav>`, `<table>` carries name, role, state, and keyboard behavior for free.

## Density band
**No density of its own — applies at every band unchanged.** Accessibility semantics are invisible (they live in the accessibility tree, not the visual layer), so a compact dashboard and a spacious marketing hero carry the *same* obligations: every control named, every interaction keyboard-reachable, focus visible. The one place density and a11y touch is **target size** — and there F52 (≥44px under a coarse pointer) and P-AY-09 (≥24px AA minimum everywhere) **override** any density rule that would shrink a hit area (the F52-over-F27 precedence in `patterns/mobile.md`). Visual density never licenses a smaller target or a removed focus ring.

## Calibrations

**P-AY-01. Every interactive control has an accessible NAME, ROLE, and VALUE/STATE in the accessibility tree (WCAG 4.1.2). Icon-only controls are the #1 failure: an icon-only button/link MUST carry a name via `aria-label`, `aria-labelledby`, or visually-hidden text — a bare `<svg>`/glyph announces nothing.**
New. *Why:* the single most-shipped AI a11y bug — a trash icon, a `×`, a hamburger, a "kebab" `⋯` with no text, so a screen reader says "button" or nothing. Role comes free from native elements (P-AY-02); name does not when the label is a glyph. Decorative icons sitting *beside* a text label get `aria-hidden="true"` so they aren't double-announced.
*Check:* tab to every icon-only control and confirm the SR (or the DOM accessibility inspector) announces a meaningful name — not "button", not "" — e.g. `aria-label="Delete row"`. Every interactive element has a non-empty computed name. Decorative-only icons are `aria-hidden="true"` or have empty `alt`.

**P-AY-02. Use the NATIVE interactive element; never `<div onclick>` / `<span onclick>` for a control (WCAG 4.1.2, 2.1.1; ARIA rule 1). A clickable thing is a `<button>` (action) or `<a href>` (navigation) — both are keyboard-focusable, Enter/Space-operable, and self-announce their role for free.**
New. *Why:* a `<div onclick>` is invisible to the keyboard (not in the tab order), announces no role, and ignores Enter/Space — the most common "mouse-only interaction" tell. The fix is almost never "add `tabindex` + `role` + a keydown handler" to a div; it is "make it a `<button>`." Reserve `role`+`tabindex`+key-handlers for genuinely custom widgets the platform has no element for (a tree, a custom slider) — and then follow the APG pattern exactly.
*Check:* every element with a click handler is a `<button>`, `<a href>`, or other natively-interactive element — grep the markup for `onClick`/`@click` on `<div>`/`<span>` and confirm zero (or each has a documented APG-widget justification with `role` + `tabindex="0"` + keyboard handlers). Tab through the page: every clickable thing receives focus.

**P-AY-03. A visible focus indicator on EVERY focusable element — never `outline:none` without an equal-or-better replacement (WCAG 2.4.7, and 2.4.11/2.4.13 in 2.2). Use the F34 ring: 2–3px accent ring, 2–3px offset, and it must clear ≥3:1 against the adjacent background (WCAG 1.4.11 — focus indicators are non-text UI components).**
Refines: F34, F15. *Why:* killing the focus outline for looks strands every keyboard user — they can't see where they are. The fix is to *restyle* focus (use `:focus-visible` so it shows for keyboard, not on mouse-click), not to remove it. The ring color is a non-text graphic, so it owes the 3:1 UI-contrast bar (not the 4.5:1 text bar) — a pale ring on a pale background fails silently the same way a low-contrast border does (F54's logic on the ring).
*Check:* `:focus-visible` defined globally; no `outline:none` anywhere lacks a visible replacement. Tab through the page and *see* the ring move on every control. Run the ring color vs. its background through `node scripts/contrast.mjs "<ring>:<bg>:focus ring"` — must clear ≥3:1 (a focus indicator is a non-text UI component, judged at the 3:1 bar, not the 4.5:1 text bar).

**P-AY-04. Logical focus ORDER and full keyboard operability (WCAG 2.4.3, 2.1.1, 2.1.2 no-trap). Tab order follows reading/DOM order; nothing is reachable by mouse but not keyboard; and there is no keyboard trap (focus can always move on, except a *modal* which traps on purpose and releases on close — P-AY-06).** Honor the conventional keys: `Esc` closes overlays, arrow keys move within a composite widget (menu, tabs, radio group, listbox), `Enter`/`Space` activate.
New. *Why:* a focus order that jumps around (because DOM order ≠ visual order, or because positive `tabindex` was used) disorients keyboard and SR users; a hover-only menu or drag-only reorder with no keyboard path locks them out entirely. Follow the APG keyboard conventions per widget — they are the shared muscle memory AT users rely on. Never use `tabindex` > 0 (it hijacks the natural order); `tabindex="0"` (in natural order) and `tabindex="-1"` (focusable only programmatically) are the only sane values.
*Check:* Tab from the top — focus moves in reading order with no surprises; Shift+Tab reverses cleanly. Every action doable with the mouse is doable with the keyboard alone. `Esc` closes any open overlay. No positive `tabindex` in the markup. Composite widgets respond to arrow keys per their APG pattern.

**P-AY-05. Document structure is conveyed by SEMANTIC HTML and ARIA LANDMARKS (WCAG 1.3.1, 2.4.1). Use `<header><nav><main><aside><footer>`, exactly one `<main>`, one `<h1>`, and a heading hierarchy that doesn't skip levels. Lists are `<ul>/<ol>`, tabular data is `<table>` with `<th scope>`, not a grid of divs.**
New. *Why:* SR users navigate by landmark and by heading — "jump to main", "next heading", "list of regions". A page built entirely from `<div>`s is a wall with no doors: no landmarks to skip between, no heading outline to scan. Skipping heading levels (h1→h3) breaks the outline the same way. A data table built from divs loses row/column association — `<th scope="col/row">` ties each cell to its headers for free.
*Check:* exactly one `<main>` and one `<h1>`; headings descend without skipping; primary regions use landmark elements (or `role="navigation/main/complementary"` if a generic element is unavoidable); each landmark of a repeated type (two `<nav>`s) has a distinguishing `aria-label`; data tables use `<table>/<th scope>`, not divs.

**P-AY-06. Modal/dialog focus contract (WCAG 2.4.3, 4.1.2; APG Dialog pattern) — defers to P-CN-10, restated here as the audit line: on open, focus moves INTO the dialog (the first focusable, or the heading via `tabindex="-1"`); focus is TRAPPED inside while open; `Esc` and a visible close both dismiss; on close, focus RETURNS to the trigger; the dialog is `role="dialog"` (or `<dialog>`) with `aria-modal="true"` and an `aria-labelledby` pointing at its title; background content is `inert`/`aria-hidden`.**
Refines: P-CN-10, F34. *Why:* the most common overlay failures are (a) focus never enters, so the keyboard user is still on the page behind; (b) focus isn't trapped, so Tab leaks onto the frozen parent; (c) focus isn't restored, so on close the user is dumped at the top of the document. All three strand AT users. This is the one place a "keyboard trap" is *correct* — but only because `Esc`/close always releases it (so WCAG 2.1.2 holds).
*Check:* open the dialog with the keyboard — focus lands inside; Tab cycles within and never reaches the page behind; `Esc` closes; on close, focus is back on the trigger button. The dialog node has `role="dialog"`/`<dialog>` + `aria-modal="true"` + `aria-labelledby`. Background is `inert` or `aria-hidden="true"` while open.

**P-AY-07. Form errors are programmatically ASSOCIATED with their field, not just visually adjacent (WCAG 3.3.1, 3.3.3, 1.3.1, 4.1.2). The input gets `aria-invalid="true"` and `aria-describedby="<errorId>"`; the error node carries that id and the recovery copy (F69). Every field has a real `<label for>` (or `aria-labelledby`); placeholder is NOT a label (P-F-01). Group related controls in a `<fieldset>` with a `<legend>` (a radio group, an address block).**
Refines: P-F-06, P-F-01, F69. *Why:* `patterns/form.md` owns *where the error sits and what it says*; this owns *the wiring that makes a SR read the error when focus enters the field*. An error message that's only visually beside the input (no `aria-describedby`) is silent to a SR user — they hear "Email, invalid entry" with no idea what's wrong. `aria-invalid` exposes the error *state*; `aria-describedby` exposes the error *text*; together they turn a visual-only error into an announced one. A placeholder vanishes on input and is never a substitute for `<label>`.
*Check:* every input has an associated `<label for>`/`aria-labelledby` (not placeholder-only); an errored field has `aria-invalid="true"` + `aria-describedby` pointing at the node holding the F69 problem-and-fix copy; tab into the errored field and confirm the SR announces label + error. Radio/checkbox groups and multi-part inputs sit in `<fieldset><legend>`.

**P-AY-08. Async / dynamic changes are announced via a LIVE REGION (WCAG 4.1.3 Status Messages). A status/success toast, an inline "Saved", a results-count update, a validation summary that appears without a focus change → an `aria-live="polite"` (or `role="status"`) region; an urgent error → `aria-live="assertive"` (or `role="alert"`). The live region must EXIST in the DOM before its content changes; injecting the whole region at announce-time often doesn't fire.**
New (cross-ref `patterns/empty-states.md` / F33 for *what* the loading/empty/error states look like — this owns how their *transitions* are announced). *Why:* a sighted user sees the toast/spinner/results-count; a SR user perceives nothing unless a live region speaks the change. "12 results" after a filter, "Profile saved", "Couldn't connect — retry" all change silently otherwise. `polite` waits for a pause (status, counts, success); `assertive`/`alert` interrupts (errors that block). Loading states: announce "Loading…" then the result, so the user isn't left in silence (pairs with the F33/P-MT-07 spinner-vs-skeleton choice).
*Check:* every UI change that happens *without* moving focus (toast, inline save confirmation, async results count, form-level error summary) is mirrored into a live region present in the DOM at load time. Trigger the change with a SR running and confirm it's announced; errors use `assertive`/`alert`, non-urgent updates use `polite`/`status`.

**P-AY-09. Target size — ≥24×24px CSS as the AA floor everywhere (WCAG 2.2 SC 2.5.8), ≥44×44px under a coarse pointer (F52 / P-MO-07). Adjacent small targets need spacing so their 24px hit-circles don't overlap, OR an inline-text exception applies.**
Refines: F52, P-MO-07. *Why:* WCAG 2.2 added a *baseline* 24px minimum that applies on **every** pointer, not just touch — so a 16px icon button on desktop with no padding fails AA even with a mouse. F52's 44px is the stronger touch bar; 24px is the floor that catches cramped desktop toolbars and dense table-row action icons. The exception WCAG carves out: targets inline within a sentence (a link in prose) are exempt, as are targets with sufficient spacing.
*Check:* every interactive target's hit area ≥24×24px on any pointer (≥44px under `@media (pointer:coarse)`, F52); cramped icon clusters get padding or spacing so the 24px circles don't collide; inline-text links are the only exemption.

**P-AY-10. State and meaning are NOT carried by color/icon-shape alone (WCAG 1.4.1 Use of Color, and the SR corollary). A color-coded status, a required-field asterisk, a chart series, an error border — each pairs its visual channel with a text/SR-perceivable one: a label, `aria-invalid`/`aria-required`, a textual legend, a `<th>`-associated value.** (The visual side of this — status double-encoding — is governed by AP23; this is its SR-perceivable requirement.)
New (the SR/non-color complement to F55/F19/AP23). *Why:* a status shown *only* as a green vs. red dot is invisible to a colorblind user *and* to a SR (color isn't in the accessibility tree). A red field border with no `aria-invalid` and no message (the P-F-06 forbidden move) fails twice — colorblind users miss the red, SR users hear nothing. The fix is a parallel text/state channel, not a second color. Note this is *distinct* from AP23 (which forbids redundant *visual* channels for sighted users): here the requirement is a *non-visual* (text/state) channel alongside the one visual channel.
*Check:* no status, error, or required marker relies on color or icon-shape alone — each has an associated text label, `aria-*` state, or programmatic value an SR/colorblind user can perceive. Required fields use `aria-required`/`required` (not just a red `*`); errors use `aria-invalid` (not just a red border).

**P-AY-11. A SKIP LINK to main content is the first focusable element on any page with repeated nav before the content (WCAG 2.4.1 Bypass Blocks). It may be visually hidden until focused (`.sr-only` + `:focus` reveal), targets `#main`, and moving to it must shift focus there (the target gets `tabindex="-1"`).**
New. *Why:* without it, a keyboard/SR user tabs through the entire header + nav on *every* page before reaching content — bypass-blocks is the canonical fix. The landmark structure (P-AY-05) provides the SR shortcut; the skip link provides the keyboard shortcut, and both should exist. The visually-hidden-until-focus pattern keeps it out of the visual design while keeping it operable.
*Check:* Tab once from page load — the first focus stop is "Skip to main content" (or equivalent); activating it moves focus into `<main>`. The link is `.sr-only` and revealed on `:focus`. (Single-region pages with no repeated nav before content may omit it.)

**P-AY-12. Reduced-motion is a hard floor — defers to `patterns/motion.md` P-MT-10 / F31 (WCAG 2.3.3). Not re-specified here; it is named so the a11y audit doesn't skip it.** Under `prefers-reduced-motion: reduce`: transform-based motion → instant/single-frame fade, looping texture killed, staggers/reveals/the signature cancelled — while the information is still fully conveyed.
Refines: P-MT-10, F31. *Why:* motion-sensitivity is Tier-1 accessibility, not preference, and the audit must confirm the fallback exists even though the rule's full recipe lives in motion.md. A surface with animation and no `prefers-reduced-motion` block is unfinished (the same way a data view without an empty state is, F33).
*Check:* a `@media (prefers-reduced-motion: reduce)` block exists and neutralizes transforms/loops/staggers/reveals; toggle the OS setting and confirm motion is reduced while the UI still fully works. (Full recipe: P-MT-10.)

## Composition defaults
- **Native first:** `<button>` for actions, `<a href>` for navigation, `<label for>` on every input, `<fieldset><legend>` for groups, `<table><th scope>` for tabular data, `<nav>/<main>/<header>/<footer>` for landmarks. Reach for `role`/`tabindex`/key-handlers only for a genuine custom widget, then follow its APG pattern.
- **One global `:focus-visible` style** (F34 ring, ≥3:1 vs background) so no control can ship without a visible focus state; `:focus-visible` (not `:focus`) so it shows for keyboard, not on mouse press.
- **One `.sr-only` / visually-hidden utility** (clip-rect, not `display:none`) for icon-button labels, skip-link text, and SR-only context — reused everywhere, never re-invented inline.
- **Skip link** as the first DOM/focus element → `#main`; landmarks + a non-skipping heading outline behind it.
- **Live region(s)** present in the DOM at load: a `role="status"`/`aria-live="polite"` for toasts/counts/saves and a `role="alert"` path for blocking errors — never injected only at announce-time.
- **Form wiring kit:** `<label for>` + `aria-describedby` (help and/or error) + `aria-invalid` on error + `aria-required` / `required`; error copy is the F69 problem-and-fix, placed per P-F-06.
- **Overlay contract** (P-AY-06 / P-CN-10): focus-in, trap, `Esc` + visible close, return focus, `role="dialog"`+`aria-modal`+`aria-labelledby`, background `inert`.
- **Targets** ≥24px everywhere (≥44px coarse-pointer); **reduced-motion** block (P-MT-10); **no color-only** meaning (parallel text/state channel).

## Forbidden moves
- **An icon-only button/link with no accessible name** — bare `×`, trash, kebab, hamburger that announces "button" or nothing (P-AY-01).
- **`<div onclick>` / `<span onclick>` as a control** — not focusable, no role, ignores Enter/Space; make it a `<button>`/`<a>` (P-AY-02).
- **`outline:none` with no visible replacement** — or a focus ring under 3:1 against its background (P-AY-03; F34).
- **A keyboard trap** (focus can't escape a region) — *except* a modal that releases on `Esc`/close (P-AY-04/06).
- **Mouse-only interactions** — hover-only menus, drag-only reorder, with no keyboard path (P-AY-04).
- **Positive `tabindex`** that hijacks the natural focus order (P-AY-04).
- **A page built entirely from `<div>`s** — no landmarks, no `<main>`, no heading outline, data tables made of divs (P-AY-05).
- **A modal that doesn't trap focus, or doesn't restore focus to the trigger on close** (P-AY-06; P-CN-10).
- **An error message only visually beside the field** — no `aria-describedby`, no `aria-invalid`; silent to a SR (P-AY-07; P-F-06).
- **Placeholder as the only label** (P-AY-07; P-F-01).
- **A toast / async result / inline save that changes silently** — no live region, so SR users perceive nothing (P-AY-08).
- **Targets under 24px on any pointer** (or under 44px on touch) (P-AY-09; F52).
- **State/meaning by color or icon-shape alone** — a red border or a green dot with no text/`aria-*` channel (P-AY-10; F55/AP23 visual side).
- **No skip link** on a page with repeated nav before content (P-AY-11).
- **Animation with no `prefers-reduced-motion` fallback** (P-AY-12; P-MT-10/F31).
