# Evidence — Search & Results (P-S calibration)

Method: studied 12 real web search/results surfaces across five contexts (in-app record search, command-palette global search, marketplace/catalog browse, search-engine-style results, and the no-results empty), read by **(a) craft to learn** and **(b) how the rules are applied** — where reality confirms a rule, calibrates a number, or breaks a rule (→ rule is wrong/too strict/needs scope). The strongest calibrations are the ones the no-results screens forced: this surface is judged on its empty case, and the screens disagree most there.

Screens: Databricks (Search results "simple" — right category rail + Type/Owner/Location chips), Amplitude (command-palette modal + right-rail facets + "3,639 results found in 14ms"; and a results page w/ right-rail facets + Relevance sort), Jira (search dropdown w/ typeahead + facets-in-dropdown), Mixpanel (search results + right-rail type facets + Relevance sort), Gemini (results list), Faire (3 marketplace screens — left filter rail w/ search-within-facet, top filter pills, "2 filters applied · Clear all", "22,184 participating brands", Sort by Featured, media-card grid), Relevance AI (marketplace "Results for design" — top filter dropdowns + media cards), Firecrawl (web/news results w/ "only show 10 results" honesty), Dovetail (no-results + illustration + "adjust your search filters"), a screen-library tool (no-results "Try these popular searches" + query chips), Twist (no-results "No matches for '' · Try filtering"), Digg (no-results "Hmm, your search didn't turn up anything" — dead end), 7shifts (search form: Location/Category/Posted-by/Date-range + tabbed results). 2026-05-29.

## The dynamic-generation lesson
Search surfaces vary on **two axes at once**: *how central filtering is* (drives facet placement — left rail when filtering IS the job/marketplace, right rail when it's optional refinement over a query, top bar when there are ≤5 facets) and *what the user decides on* (drives item shape — a title → list row, an image → media card, a snippet → rich row). A marketplace (Faire) is left-rail + media-grid + infinite scroll; an in-app record search (Amplitude/Databricks) is right-rail + list-rows + relevance-sort; a global command palette (Amplitude modal, Jira dropdown) collapses the whole thing into a focused overlay with facets-in-dropdown. The constant is the *reading order* — input → count+echo → active-filter chips → sort → results → (and always) the four states; the **facet placement and item shape flex to the content and the centrality of filtering.** Stamping a left rail onto a two-facet query search, or a media grid onto a title-only record search, is the proof it was templated, not reasoned.

## Over-strict / wrong-rule catches (the strongest calibrations)
- **Digg's "Hmm, your search didn't turn up anything"** echoed the query but offered *no recovery* — proved that "ship a no-results state" (F33) isn't enough; the state must be *actionable* (broaden / clear-filters / suggest), not just present. Fed the forbidden "dead-end no-results" and sharpened P-S-09 against F69. (Mirrors the detail study's HubSpot-`(0)` catch: an empty state is a *designed, actioned* state, not a polite blank.)
- **Comparing the no-results screens (Twist, Dovetail, the suggested-query empties)** showed the no-results state and the first-run state are *different messages* that lazy designs collapse into one — first-run has no query echo and is suggestive; no-results quotes the query and is corrective. Fed P-S-10 (never reuse one for the other) — a tell invisible to every rule check because each state looks fine alone.
- **Faire's "2 filters applied · Clear all"** proved active filters need *removable chips + a clear-all*, not just a rail of checked boxes — because the most common cause of a near-empty result list is over-narrowing, and the user's recovery is "clear filters," which has to be one tap from the chip row (P-S-04 → P-S-09).
- **Jira's facets-inside-the-search-dropdown** broke the naive "facets live in a rail on the results page" assumption — the fastest refinement happens *in the typeahead dropdown*, before a results page loads at all (P-S-02). The results page is the fallback, not the only home for facets.

## Calibrations applied to patterns/search.md
1. Search input → **anchor, scope-naming placeholder, magnifier + clear, ≥44px** (P-S-01).
2. Typeahead → **recents/suggested + quick facets in the dropdown** (P-S-02).
3. Header → **count + echoed query first**, timing aside optional (P-S-03).
4. Active filters → **removable chips + "Clear all" at ≥2** (P-S-04).
5. Sort → **one select, top-right, Relevance default for a query** (P-S-05).
6. Facets → **contextual placement** (left=marketplace / right=app-over-query / top=≤5 / drawer=mobile) — the dynamic branch (P-S-06).
7. Result item → **contextual shape** (row / media card / rich row) by what the user decides on (P-S-07).
8. Paging → **infinite for browse, explicit for find-a-record; keep count+filters visible** (P-S-08).
9. States → **first-run ≠ loading ≠ no-results ≠ error**, each its own message; no-results echoes the query + a recovery path (P-S-09/10).
10. Matched term → **highlight it; chips carry it for facet-only browse** (P-S-11).
