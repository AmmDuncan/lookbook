# Evidence — Container choice (modal vs slideover vs page) (P-CN calibration)

Method: studied 16 real **web** screens across four flow shapes — a flow rendered as a **modal dialog**, as a **side slideover/drawer**, and as its **own full page/route** — read by **(a) craft to learn** and **(b) how the choice maps to the flow** (its length, whether it interrupts or is a destination, whether the parent context must stay visible, whether the action repeats down a table, whether it needs a shareable/refresh-safe URL). This is a **cross-cutting decision guide** (like the mobile reflow grammar), not a surface archetype — the read is *why this flow took this container*, and the strongest calibrations are the consistent factor→container mappings real products converged on. 2026-05-29.

Screens — **Modal**: Navattic ("Create interest" — one Name field + Cancel/Create), Kiwi.com ("We need a few final details" — 2 name fields mid-checkout, the booking summary frozen behind the scrim), Whop ("Add FAQ" — Question + Answer, Add disabled until valid), Manus ("Add Knowledge" — Name/Use-when/Content over a settings page). **Slideover / drawer**: Copy.ai (Infobase edit panel — name/tags/text over the Infobase list), Remote ("Edit table" column-visibility panel over a 2,183-row candidate table), Origin (transaction edit panel — type/desc/merchant/amount/category/date over a 1,192-row spending table; edit one row, close, edit the next), Base44 ("User Schema Editor" read panel over a Users table), Google AI Studio ("Editor settings" toggles panel over the code editor), Maze ("Settings" panel — Move / Delete quick-actions + password + integrations over the maze builder), Whop ("Edit gallery" media panel over the app-details page). **Page / route**: Mercury (company-verification **1/6** stepped page, left step-rail), ElevenLabs (book-publish multi-step page, left step-rail + `Cancel` / `Save & exit`), Deputy (job-application **Contact details** step of a 6-step page), Booking.com ("Partner verification" 4-step page, numbered progress bar). 2026-05-29.

None deep-linkable; none needs the parent visible *while* editing | **NEW → P-CN-01/02**: modal = short, interruptive, resolve-or-dismiss-now; ≤ ~5 fields; not deep-linkable, not the destination. Primary + a real Cancel; disabled-until-valid (Whop) is fine. |

When the user must not lose their place AND can't act on the parent meanwhile, modal beats slideover. |
| **Slideover** — Copy.ai Infobase edit, Origin transaction edit, Whop edit-gallery, Remote column editor | **Quick-edit while the list/parent stays LIVE beside it.** The panel slides from the right (~360–480px); the table/page remains visible and (often) still interactive on the left; medium content (4–8 fields) | **NEW → P-CN-03**: slideover = peek/quick-edit keeping the parent **visible and in place**; medium content; the spatial context (which row, which page) is preserved, not frozen. |
| **Slideover** — Origin: edit a transaction, close, edit the next, down 1,192 rows | **Rapid repeat down a table.** The panel opens on row N, you save, it closes, you open row N+1 — no full-page nav per edit, no lost scroll position | **NEW → P-CN-04**: rapid repeated actions across rows of a table belong in a slideover — full-page-per-row would thrash navigation and scroll. |
| **Slideover / drawer** — Maze "Settings" (Move / Delete / password / integrations) | **Contextual config beside the thing it configures.** Note: `Move` and **`Delete` (destructive)** live *inside* the panel as labelled rows — but they are one-step, low-stakes-per-tap actions, not a bare "are you sure?" gate | **CALIBRATE → P-CN-02 nuance**: a *destructive confirm* (the "are you sure, this can't be undone" gate) is a **modal**; a destructive *option* sitting among settings is fine in a drawer — the confirm it triggers is the modal. |
| **Slideover** — Base44 schema viewer, Google AI Studio editor settings | **Peek without leaving.** Read-mostly reference / toggles you flip while watching the main canvas; closing returns instantly to the unchanged parent | **CONFIRM → P-CN-03**: the slideover's other job is a *peek* — inspect or adjust while the workspace stays put. |

## The factor → container map (the decision this guide encodes)

| Factor | Modal | Slideover / drawer | Page / route |
|---|---|---|---|
| **Length** | short (≤ ~5 fields) | medium (4–8 fields) | long / multi-step / content-rich |
| **Posture** | interruption (resolve-or-dismiss now) | peek / quick-edit | destination (the user's main focus) |
| **Parent context** | frozen (dimmed, inert) behind a scrim | visible & in place (often still live) | replaced (you navigated to it) |
| **Deep-link / share / refresh-safe** | no (unless routable — see P-CN-07) | no (unless routable — see P-CN-07) | **yes** (the whole reason) |
| **Rapid repeat across rows** | no | **yes** (open row N, save, open N+1) | no (nav thrash) |
| **Destructive confirm** | **always** (the "are you sure" gate) | the destructive *option* may live here; its confirm is still a modal | no (don't make a destroy a full-page nav) |
| **Would it nest another overlay?** | that's the smell — promote to a page | same | n/a (it's already a page) |

## The dynamic-generation lesson
The container is **not** a stylistic preference — it is computed from the flow's *shape*. Five factors decide it, and they mostly agree: a 2-field "name us" prompt that must resolve before checkout continues is **short + interruptive + frozen-context + not-linkable** → every arrow points at a **modal** (Kiwi.com, Navattic). A "tweak this transaction, then the next, then the next" edit is **medium + repeated-down-a-table + parent-stays-live** → **slideover** (Origin). A 6-step KYC submission is **long + multi-step + the-user's-focus + must-be-resumable-by-link** → **page/route** (Mercury, Booking.com). Where the factors *disagree* — "I want overlay convenience AND a shareable URL" — the **routable overlay** (P-CN-07) resolves it: the URL addresses the item, the route parent renders it as a slideover/modal. Picking the container by tallying these factors (not by reaching for the same dialog every time) is the proof the flow was reasoned about, not stamped.

## Over-strict / wrong-rule catches (the strongest calibrations)
- **Maze's `Delete` inside a settings drawer** caught a naive "destructive is always a modal" as *too coarse*: the destructive *option* can sit among other settings in a drawer — it's the **confirm gate** it fires that must be the modal. Fed P-CN-02's nuance (destructive *confirm* = modal; destructive *option* among settings = wherever the settings live).
- **Origin's edit-one-row-then-the-next over 1,192 rows** showed slideover isn't just "a wider modal" — its defining job is **keeping the list live for rapid repeat**, which a modal (frozen parent) and a page (nav-per-row) both break. Fed P-CN-04.
- **Every wizard carried a step indicator in the page chrome** (`1/6`, numbered bar, left step-rail) — proving multi-step *needs* the page's room for durable progress and that the step belongs in the **URL**, not in overlay state that a refresh would wipe. Fed P-CN-05/06.
- **Kiwi.com's frozen-but-visible booking summary** sharpened the modal-vs-slideover line: both keep the parent on screen, but modal **freezes** it (dimmed, inert) while slideover keeps it **live** — the choice is whether the user needs to *act on* the parent while the panel is open. Fed P-CN-02 vs P-CN-03.

## Calibrations applied to patterns/containers.md
1. **Modal** = short, interruptive, resolve-or-dismiss-now, frozen parent; destructive confirms always; not long-form, not deep-linkable, not modal-on-modal (P-CN-01/02).
2. **Slideover / drawer** = peek or quick-edit with the parent **visible & in place**; medium content; rapid repeat down a table (P-CN-03/04).
3. **Page / route** = a destination — long/multi-step/content-rich, the user's focus, deep-linkable & refresh-safe; the step lives in the URL (P-CN-05/06).
4. **Routable overlay** escape hatch resolves "overlay convenience + shareable URL": parent route owns the URL, panel owns the view (P-CN-07).
5. **Would-it-nest-another-overlay** is the smell that says *make it a page* (P-CN-08).
6. **Mobile collapse** defers to P-MO-09 (modal→sheet, slideover→full-screen/sheet) (P-CN-09).
7. **Overlay a11y basics** — focus in, return focus to trigger, scrim, always-dismissible (P-CN-10).

### Over-strict / wrong-rule catches (run 2)
- **Slideover rich-edit cap was too low.** Run 1 said "up to ~560px"; QuickBooks' supplier/edit-account drawers read ~560–640px and a major bank DS fixes slide-outs at 512px. Real record-edit drawers cluster ~480–560 and content-heavy ones reach ~600–640. → **CALIBRATE P-CN-03** (and the slideover composition default).
- **Destructive-confirm chrome was under-specified.** Run 1 nailed "destructive confirm = modal" but didn't capture that excellent products *scale the confirmation friction to the blast radius* (type-the-name vs ack-checkbox vs enumerate-collateral). Eight independent products converge on this. → **NEW NUANCE to P-CN-02** (not a new rule — a clause on the existing destructive-confirm rule).
- **The drawer→page escalation link is the *positive* P-CN-08.** Run 1 framed P-CN-08 only negatively ("don't nest → make it a page"). Three products show the constructive move: the peek drawer ships an explicit "full profile / open page" link. → **REFINE P-CN-08** to name the escalation affordance (still no new rule).
- **No TOO-STRICT catches that loosen a rule this run** — the Salesforce long-form-modal is the rule's *forbidden* case in the wild (confirms, doesn't refute). Modal width 480–560/640 and the wizard step-indicator both VALIDATED hard against external design systems.

### Net for run 2
- **VALIDATED (unchanged):** P-CN-01 (modal width 480–560/640 + ≤~5-field shape), P-CN-04 (rapid-repeat slideover), P-CN-05/06 (page = multi-step + step-in-URL + durable step chrome), P-CN-07 (routable overlay), P-CN-09, P-CN-10.
- **CALIBRATE:** P-CN-03 slideover rich-edit width cap ~560 → real cluster 480–560 with content-heavy record panels reaching ~600–640; update the composition default to match.
- **NUANCE (no new rule):** P-CN-02 — destructive confirm scales its gate to blast radius (typed-name/phrase for irreversible high-stakes; ack-checkbox for lesser; may enumerate collateral).
- **REFINE (no new rule):** P-CN-08 — name the *positive* escalation: a peek drawer offers an explicit "open full page / full profile" link rather than nesting an overlay or ballooning the drawer.
- **PARKED / NEW-RULE CANDIDATES (flag, do not add):** (a) drawer→page escalation link as its own rule — folds into P-CN-08, don't promote; (b) per-step time-estimate on wizard checklists (Coinbase) — taste, not a rule; (c) `Save & New` / `Save and add another` power-create affordance on create modals (Basecamp, Salesforce) — a form-pattern (P-F) concern, not a container one.
