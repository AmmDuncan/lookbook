# Evidence — Identity (brand → token system) (P-ID calibration)

Method: Identity is **how a brand input (color, voice, one adjective) becomes a coherent token set + design DNA** — so this is a reverse-engineering study, not a pixel-measurement calibration. I pulled real, public, shipped products that share an *archetype* (settings panel · billing/pricing · workspace dashboard) but feel like completely different products, and read each backwards: *which token-level choices (accent + on-color step, type pairing, radius, density, shadow/border weight, motion register) make this feel like ITSELF — and is the distinctiveness coming from the SYSTEM or from decoration?* The goal was to test the central thesis of this file: **identity lives in the token system and composition discipline, never in sprinkled motifs.** It holds — every distinctive product studied earns its character through accent/type/density/radius dials and spends its accent scarcely (F17), and none decorate their functional surfaces. Studied against real public products; the reference aggregator used to surface them is not a calibration source and is deliberately unnamed. 2026-05-29.

Screens — same-archetype, different-DNA set: **Monarch** (workspace settings + billing — deep navy accent, tight rows, sharp-ish radius, near-mono trustworthy fintech), **Sprig** (billing & plans — warm butter-yellow accent, rounded pills, airy spacing, friendly consumer-research tool), **Graphite** (workspace billing — near-mono with a single restrained blue, crisp dense dev-tool register, status-only color), **Framer** (change-plans — saturated electric-blue primary, one violet secondary used *only* on the upgrade tier, clean white cards), **Lovable** (plans & credits modal — indigo→violet brand register held to the CTA, otherwise neutral), **Pitch** (billing — dark surface, thin display wordmark, a single gradient hairline on the summary card as its one expressive moment), **Zoom** (subscription config — corporate blue, low chroma, maximally restrained). Plus web research on Stripe / Linear / Vercel / Notion token discipline. 2026-05-29.

## The system-not-decoration lesson
Monarch, Sprig, Graphite, Framer and Lovable could be assembled from one component kit — same cards, same pricing tiers, same settings rows. They feel like five different companies **entirely because of the token DNA**: navy-tight-cool vs yellow-round-airy vs mono-dense-crisp vs electric-two-tone vs indigo-restrained. Not one of them stands out by adding a glyph to a stat tile, a motif to a row, or a decorative icon to a card — the functional surfaces are uniformly restrained, and the distinctiveness is carried by **accent hue + on-color step + neutral temperature + radius + density + shadow weight**, with accent spent ≤5× (F17). The two products with a visible expressive flourish (Framer's violet tier, Pitch's gradient hairline) place it on the *part-expressive* element (the pricing card) and keep it removable — never on the chrome. This is the proof for the file's spine: **applying identity outputs a token skin + restraint rules, not ornaments.** The web research on Stripe / Linear / Vercel / Notion says the same thing in words — single type family used systemically, a monochrome neutral foundation carrying ~80% of the work, brand hue traced lightly through shadow/text temperature, accent measured — "the one color decision that makes a UI look expensive" is *scarcity*, not a signature.

## Over-strict / wrong-rule catches (calibrations applied)
- **A naive identity rule could read "give the product a recognizable motif."** The whole same-archetype set disproves it: identity came from dials, and the one prior attempt to encode "signature flourishes" (the dropped Variation catalog) drove a clean dashboard to add decorative KPI icons + double-encoded status and looked *worse*. → **P-ID guardrail (P-ID-09)**: functional surfaces get ZERO decorative identity; identity there shows only through token discipline. The signature lives on expressive surfaces and is removable (P-ID-08), cross-ref AP20/AP23/AP24 and P-AP-07.
- **F66 has two branches, and the wild shows both.** Monarch's navy *is* the white-text step; Sprig's yellow forces **dark ink**. → **P-ID-02** makes deriving (or darkening to) a white-text-capable tonal step a hard gate, with the dark-ink-on-light fallback named — verified with `scripts/contrast.mjs`.
- **A secondary accent is not a free second color.** Framer's violet appears only on the Pro tier; the token system already bounds `--accent-secondary` to hero/CTA. → **P-ID-03** keeps the ramp single-accent + one optional bounded secondary, never a multi-hue palette.
- **Display fonts are optional, not a distinctiveness requirement.** Graphite/Zoom/Monarch ship a single workhorse sans and read as fully themselves. → **P-ID-04** keeps F1's "display face optional, per-project" — a display face is warranted only on expressive/editorial/luxe register, never as a default "add character" move.

## Calibrations applied to patterns/identity.md
1. **Identity = derive a token system, not invent a motif** — the spine; output is a `:root` skin + restraint rules (P-ID-01).
2. **Accent ramp must include a white-text-capable dark step (F66), or use dark ink on a light accent** — gated with contrast.mjs (P-ID-02).
3. **One accent + one optional bounded secondary**, never a multi-hue brand palette on UI (P-ID-03).
4. **Display face stays optional/per-register** (F1) — warranted on expressive/editorial, never a default character-add (P-ID-04).
5. **Density · radius · shadow · border-weight are personality dials** that map register→values: tight+sharp+flat+hairline = technical; airy+rounded+soft = friendly-consumer (P-ID-05/06).
6. **Motion character is a dial too** — cross-ref motion.md, derived from the same adjective (P-ID-07).
7. **One signature, expressive surfaces only, removable** — cross-ref P-AP-07 / personality.template.md (P-ID-08).
8. **Functional surfaces get zero decorative identity** — the dropped-Variation guardrail, restated (P-ID-09).
