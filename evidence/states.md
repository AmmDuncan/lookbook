# Evidence — State handling / unhappy paths (P-ST calibration)

Method: studied ~30 real web screens across the states F33 names but most products ship cheaply (loading, error) plus the ones F33 doesn't enumerate at all (partial failure, pending, offline, stale-while-revalidate, optimistic+rollback, success), from a reference study of real, public, shipped products, supplemented by the established server-state/resilient-UI literature for the mechanics that don't show in a still (optimistic rollback, request identity, error boundaries, SWR). Read by **(a) craft to learn** and **(b) how the rules apply** — where reality confirms a rule, calibrates a number, or shows a rule needs *scope*. The strongest reads here are two *scope* catches: error-treatment is not one thing (it scopes field → section → widget → page, and reality drew every band cleanly), and loading is not one thing (skeleton-when-layout-known vs spinner-when-unknown, also drawn cleanly). 2026-05-29.

## Mechanics not visible in a still (literature-grounded, flagged)
- **Optimistic UI + rollback (P-ST-07)** can't be captured from a screenshot. Grounded in server-state practice: apply instantly, reconcile on response, snapshot-rollback on failure; assign each mutation a **request identity** so only the latest commits/rolls back and stale responses are ignored; a failed mutation must roll back *and tell the user* (a quiet toast — never a silent revert). The line: reversible-and-cheap ⇒ optimistic; consequential-or-slow ⇒ pending-then-confirm. Flagged in the pattern as literature-grounded, not screenshot-observed.
- **Partial failure (P-ST-06)** rarely shows in a single curated capture (you'd need a multi-fetch surface with one fetch down). Grounded in resilient-UI practice: wrap risky *regions* in lightweight boundaries showing a local fallback + retry that doesn't block the page; a *partial rollback* (keep the change visible but marked "failed, retry") is sometimes friendlier than a hard revert. Reasoned from P-ST-03's confirmed scope finding + the literature.
- **Stale-while-revalidate (P-ST-09)** swap-in-place and "never persist known-stale" is an SWR/Query contract (revalidation ditches the in-flight request and never displays stale once fresh arrives). Canva is the closest still; the rule's "never re-skeleton a populated screen" is grounded there + DVLA's SW `NetworkOnly`-for-API lesson (never blanket-cache API GETs).

## The dynamic-generation lesson
State handling varies by **what is true and what failed, not a template**: the *truth* (loading / empty / error / offline / stale) picks which treatment; the *scope of the failure* (field / region / route) picks how big the error is; the *expected wait + known-ness of the layout* picks skeleton-vs-spinner-vs-optimistic; the *reversibility + stakes* of a mutation picks optimistic-vs-pending; the *weight of the action* picks toast-vs-screen for success. The constant is the discipline — every state is truthful, correctly scoped, recoverable, and announced (`aria-live`) — but the treatment flexes to the situation. Stamping one "loading spinner" + one "error page" across every surface is the tell, the same way one generic "empty" component is the P-ES tell.

## Over-strict / wrong-rule catches (the strongest calibrations)
- **Loading is not one treatment — skeleton-vs-spinner is a *decision*, gated on whether the layout is known.** A naive "always use a skeleton" would have flagged Threads/Canva's correct spinner (unknown content shape); "always spinner" would have lost the zero-reflow win Vercel/Neon/Quicken got from layout-mirroring skeletons. The deciding variable reality showed is *is the layout predetermined* (+ wait length), not a flat rule. → P-ST-01/02.
- **Error is not one scope.** Reality drew four bands cleanly: New Yorker (field), Linktree (section banner), Remote (region with chrome intact), Threads/PayPal (full page). A flat "show an error page" would over-scope a field validation into a viewport-blanking interstitial. → P-ST-03/04/05, mirroring P-ES-10's scope finding.
- **Background refetch must not re-skeleton.** Canva keeping its gallery laid out (vs blanking to grey) shows the right instinct; the forbidden move is the regression of taking readable content away to show skeletons on every revalidation. → P-ST-09.

## Gaps / reasoned-not-observed
- **Partial failure** and **optimistic rollback** are mechanics, not stills — reasoned from P-ST-03's confirmed scope finding + server-state/resilient-UI literature, flagged as such in the pattern (P-ST-06/07).
- **Offline degraded-but-usable banner (P-ST-10)** — P-ES already captured the *full-page* offline moment (Quicken/Udemy); the in-app auto-retrying banner over still-usable content is reasoned from F73 (transient, not the user's fault) + the resilient-UI "keep content usable" principle, deferring the full-page case to P-ES-06.

## Calibrations applied to patterns/states.md
1. **empty ≠ error ≠ loading** truth-split is the spine + the #1 forbidden move (empty-for-failed-load).
2. Loading → **skeleton when layout known + wait ~300ms+, spinner when unknown/tiny/short, optimistic under ~100–300ms** (P-ST-01); **skeleton mirrors the layout** (P-ST-02).
3. Error → **scope matches failure** (field/section/region/page — P-ST-03/04), **calm + retry + code-as-fine-print** (P-ST-05, extends P-ES-03).
4. **Partial failure** is its own state — render what loaded, scope the failure + retry (P-ST-06).
5. Mutations → **optimistic+visible-rollback for reversible-cheap; pending+confirm for consequential-slow** (P-ST-07); **trigger owns the wait, result = toast** (P-ST-08).
6. **Stale-while-revalidate** keeps content live, swaps in place, never persists stale (P-ST-09).
7. **Offline** = unobtrusive auto-retrying banner, content usable (P-ST-10, defers full-page to P-ES-06).
8. **Success proportional to stakes** — toast / inline / screen (P-ST-11).
9. **a11y announce + reduced-motion** on every state change (P-ST-12, Tier-1).

### NEW-RULE CANDIDATEs surfaced this pass
None promoted. Two adjacent ideas were considered and **parked, not added** (refine-don't-add; battle-test bar not met, and each is already covered or out of scope):
- *Timeout / "this is taking longer than usual" escalation* (a slow request crossing ~10s switches its indicator copy to acknowledge the wait + offer cancel/retry). Reasonable, NN/g 10s-threshold-adjacent — but it's a *refinement of P-ST-01's wait-band thinking*, not a new state, and risks rule-bloat on a surface already at 12 rules. Park for battle-test only if a real surface shows the current band failing.
- *Retry with backoff / "retrying… (attempt 2)" affordance* — an implementation detail of P-ST-05/P-ST-10's retry, not a distinct user-facing state. Stays folded into those rules.
