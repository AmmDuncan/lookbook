Drill-down axis study · one capability · four axes

Role-gated UI studies

One capability — verify a deposit slip — and one user who does not hold it: a branch cashier. Sixteen renderings. As with the form sheet, several are wrong on purpose, because hide-versus-disable is not a matter of taste once you ask whether the user can obtain the access.

The deciding question, asked before anything is drawn: can this user ever hold this capability? If never — hide it; showing it is a tease. If yes, through a request or a scope change — show it and say how. Most bad gating is this question going unasked.

Cast: deposit.verify, held by branch managers with national scope. Viewer is Ama Serwaa · Cashier (CSA), Accra North — a role that can be granted it.

A UI gate is visibility, never the security boundary. Every frame here assumes the server refuses POST /deposits/:id/verify regardless of what is drawn. If a variant looks unsafe, the objection is with the endpoint, not the pixels — and a gate that only exists in the client is a bug in both places.

Axis A

What the blocked control does

Four treatments of the same Verify button. The difference between them is entirely about what the user is told, and whether the telling leads anywhere.

Rule: hide what the role can never hold; show, explain and route what it could. Never ship a disabled control with no reachable reason — it reads as a broken product, and the user's next move is to email someone. NN/g on disabled states · in-repo precedent: soft-warn-with-confirm, RoleEditor.vue
A1Hidden entirely △ Depends
The row still renders; the action simply is not there. Correct when the role can never hold the capability — nothing to explain, no route to offer, so the honest UI has no hole in it. Wrong for our cast: Ama can be granted deposit.verify, so hiding it removes a route she should be offered. Same pixels, opposite verdict, decided entirely by whether the access is obtainable.
no control · no trace · right for a role that can NEVER hold it

Axis B

The same capability, four surfaces

One capability rarely appears once. deposit.verify shows up in the nav, on a page, in a section and on a row — and the gate has to answer for all four, consistently, or the user learns the product is arbitrary.

Rule: pick one policy per capability and apply it everywhere it surfaces. The failure is mixing — a nav item that hides but a row action that greys out teaches nothing, and the user cannot form a model of what they are allowed to do.
B1Nav item
The gated destination is listed but marked, so the shape of the product stays learnable. Hiding it instead is also defensible — what is not defensible is hiding it here and greying it on the page it leads to.
listed + lock marker + muted ink · not removed, not a dead link

Axis C

Whole-page denial

What a gated URL returns when the user arrives at it directly. The choice leaks information, so it is a product decision and a security one at the same time.

Rule: tell the truth unless the existence of the resource is itself confidential. A 404 for something the user knows exists trains them to distrust the product; a 403 for something secret leaks that it is there. The DVLA default is C2 — internal staff tooling, nothing here is secret from staff.
C1Hard "not found" △ Depends
Correct only when confirming the page exists would itself leak something — another branch's case, another tenant's record. Used as a general-purpose gate it is a lie the user can disprove, because a colleague's screen shows the page.
reveals nothing · lies when existence is not secret

Axis D

How far the explanation goes

Four rungs of the same ladder. Each adds one piece of information, and each costs more to build — the right rung depends on how often the grant actually happens.

Rule: climb until the user's next step is unambiguous, then stop. A capability granted twice a year does not need a request workflow; one granted weekly should not be routed through a colleague's memory.
D1Blocked, nothing said ✗ Avoid
The zero rung. The user knows only that something did not work — indistinguishable from an outage, and unactionable.
no reason · no owner · no route

Lifting from this sheet: the answer for most capabilities is A4 or A3 for the control, B3 for the surface, C2 or C3 for the route, and D3 for the explanation — climbing to D4 only where the grant is routine. The one rule that outranks all of it: whatever is drawn, the server refuses the call anyway. A gate that exists only in the client is not a gate.
