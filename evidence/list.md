# Evidence — CRUD list / index page (P-L calibration)

Method: studied 14 real web list/index pages across six domains (admin data-grid, users/members management, orders/transactions, knowledge articles, agent-task queue, project/file galleries), read by **(a) craft to learn** and **(b) how the rules are applied** — where reality confirms a rule, calibrates a number, or reveals one as too strict / mis-scoped. Reading reality is what catches the over-strict guess; the strongest calibrations below are rules that real screens *bent*.

Screens: Braintrust (playground data-grid), HubSpot (Lists — Manage), Salesforce (Knowledge — All Articles), Relevance AI (Tasks + filter popover), Mixpanel (Users), Asana (Admin Users — 2 selected bulk bar), User Interviews (Designers — row overflow + select-all), monday.com (people-100 colored-cell grid), Squarespace (Orders), Shopify (Orders — list view + 1-selected bulk bar), Time2book (Catalog — Orders tab), Programa (Projects card grid), Dovetail (project-template picker grid), Figma (Team project — file grid + view toggle). 2026-05-29.

## The dynamic-generation lesson
List pages vary on **two independent axes**: (1) **table vs card grid** — does the record's identity read visually (a design file, a project with a cover, media → card) or as structured facts (an order, a user, an article → table); and (2) **paginate vs scroll** — does the user navigate to a *page* of records (orders, articles → numbered pagination with a count) or scan a continuous *stream* (tasks, a spreadsheet of rows → virtualized scroll). The constant is the *anatomy* — title + count, a quick-filter/saved-view strip, a one-row toolbar (search-left, filter/sort-center, one primary-right), the records, a selection→bulk-bar, and a pager. The table-vs-card and paginate-vs-scroll picks flex to the content; getting them right is the proof the layout was reasoned from the records, not stamped from a template.

## Over-strict / wrong-rule catches (the strongest calibrations)
- **Salesforce's five-button toolbar** (New/Publish/Assign/Archive/Delete) showed that a list toolbar accretes verbs that actually act on *selected rows* — they belong in the bulk-action bar (P-L-06), not the resting toolbar. Without seeing it, the naive rule would have allowed a multi-button toolbar. Fed P-L-01's "one primary only" + the action-soup forbidden move.
- **No admin list used a left filter rail.** The instinct to give a list page a faceted left rail (carried over from e-commerce search) is wrong for the everyday admin index — HubSpot/Shopify/Asana/Mixpanel all use inline chips or a popover. Fed P-L-07's "rail only when filter-heavy; inline/popover otherwise" and the forbidden "filter rail for 2 filters."
- **Mixpanel's wall of "undefined"** and **monday's colored gender cells** proved the failure isn't layout — it's letting raw null leak through (format it, or "—") and spending status-color on non-status data. Fed the forbidden moves and tie them back to F72/F19.

## Calibrations applied to patterns/list.md
1. Toolbar → **one row: search-left, filter/sort/columns-center, one primary "New X"-right**; verbs-on-rows go to the bulk bar (P-L-01).
2. Quick-filter / saved-view **tab strip between title and toolbar** (P-L-02).
3. **Table vs card grid contextual** on visual-vs-structured identity — the dynamic branch (P-L-03).
4. **Columns carry hierarchy** — identity link, 2–4 earning facts, status pill, right-aligned numerics, muted tail (P-L-04).
5. Row affordance → **identity links + whole-row click; one explicit secondary; rest in a ⋯ menu** (P-L-05).
6. **Selection reveals a bulk-action bar** with count + set-verbs + clear-✕ (P-L-06).
7. Filters → **inline chips for 1–3; popover builder for richer; rail only when filter-heavy** (P-L-07).
8. **Paginate (with count) vs infinite-scroll/load-more contextual** on navigate-to-page vs scan-stream (P-L-08).
9. **Full state set** — skeleton rows, first-run empty ≠ filtered-no-match empty, scoped error (P-L-09).
