# Pattern: Container choice (modal vs slideover vs page)

**Inherits:** all of `fundamentals.md` unless overridden below.
**Cite as:** `P-CN-<nn>`.

> **This is a cross-cutting decision guide, not a surface archetype.** Like the mobile reflow grammar (`patterns/mobile.md`), it owns *one decision that every other pattern reaches for*: when a flow opens as a **modal dialog**, a **side slideover / drawer**, or its **own page / route**. The surface patterns own *what the flow is*; this guide owns *which container holds it*. The form pattern's entry-vs-settings split (P-F) already implies "page or overlay?"; this guide makes that decision explicit and adds the third axis (modal vs slideover). It governs the **desktop** decision; the **mobile** collapse of each container defers to **P-MO-09** (modal→bottom-sheet, slideover→full-screen/sheet) — don't re-specify it here.

## Surface intent
Not a surface of its own — a **choice applied before a flow is built**. The user is trying to do one thing (create a record, edit a field, complete a sign-up, confirm a delete), and the question is *where that thing happens*: floating over a frozen page, sliding in beside a live one, or as a destination they navigated to. The wrong container is a quiet, pervasive tell — a 12-field form crammed into a tiny modal, a "share this" overlay that has no URL, a destructive confirm that navigates the whole app away, a primary destination demoted to a slideover. The right container falls out of the flow's *shape*: its **length**, whether it **interrupts or is a destination**, whether the **parent must stay visible**, whether the action **repeats down a table**, and whether it must be **deep-linkable / refresh-safe**. Decide by tallying those factors, not by reaching for the same dialog every time.

## Density band
**Inherit the flow's own band — the container does not change it.** A short create-form in a modal keeps form density (F26 medium: 44–48px fields, 16–20px field gap, P-F); a settings drawer keeps settings density; a multi-step page keeps the entry-form rhythm. The container sets *chrome* dimensions, not content density: modal width ~480–560px (single-column) up to ~640px (a conceptual pair), slideover ~360–480px (peek/edit) up to ~560px (richer edit), page = the archetype's normal measure inside the app shell. Inner padding 24–32px desktop in all three (F10/F27). Texture: none — these are product-action surfaces (F36 compact/medium band).

## Calibrations

**P-CN-01. MODAL = short, interruptive, resolve-or-dismiss-NOW. Use it for a flow of ≤ ~5 fields (or a single decision) that the user must complete or cancel before continuing — and that does NOT need to be deep-linkable, content-rich, or able to spawn another overlay.** One primary verb + a real Cancel/dismiss; the primary may be disabled-until-valid. Centered, ~480–560px, scrim behind.
New. *Why:* the modal's whole nature is interruption — it floats over and blocks until resolved. Real modals are tight: Navattic "Create interest" (one Name field), Whop "Add FAQ" (2 fields), Manus "Add Knowledge" (3) — all ≤3 fields, button-triggered, primary + Cancel (`evidence/containers.md`). Past ~5 fields or any multi-step shape, the modal stops being a quick interruption and becomes a cramped page (the forbidden 12-field-in-a-modal tell).

**P-CN-02. MODAL keeps the parent FROZEN (dimmed, inert) behind a scrim — and a destructive CONFIRM is ALWAYS a modal.** Use a modal when the user must not lose their place *and* has no reason to act on the parent while the panel is open (Kiwi.com freezes the booking summary behind "We need a few final details"). Every "are you sure — this can't be undone" gate is a small centered modal with calm, factual copy (F73), the destructive verb named (F68: "Delete project", not "OK"), and the safe option as the easy dismiss.
New. *Why:* the frozen-context modal returns the user exactly where they were (Kiwi.com). And a destructive confirm must *block* — it can't slide in beside live content the user might keep clicking, and it must never be a full-page navigation. Nuance from the evidence: a destructive *option* may live among other settings in a drawer (Maze's `Delete` row), but the **confirm it fires** is the modal. Two equal-weight buttons are forbidden (F16/AP18); destructive-primary + ghost-cancel, never the reverse-weighted trap.

**P-CN-03. SLIDEOVER / DRAWER = peek or quick-edit while the parent stays VISIBLE and in place. Use it for medium content (4–8 fields, a properties panel, a read-mostly inspector) where the spatial context — which row, which page — must be preserved, not frozen.** Slides from the right (LTR), ~360–480px, the list/canvas remains beside it and often still interactive.
New. *Why:* the slideover's defining trait is that the parent stays *live*, not dimmed-out (Copy.ai Infobase edit over its list; Whop "Edit gallery" over app-details; Base44 schema viewer and Google AI Studio editor-settings as *peeks* over the workspace — `evidence/containers.md`). The distinction from a modal (P-CN-02) is exactly this: modal *freezes* the parent, slideover keeps it *in place and usable*. Choose slideover when the user benefits from seeing (or acting on) the parent while the panel is open.

**P-CN-04. SLIDEOVER for rapid repeated actions down a table — open row N, save, close, open row N+1 — without per-row navigation.** When the same edit recurs across many rows, the slideover preserves scroll position and the list's identity so the user can run the action in a loop.
Refines: P-CN-03. *Why:* Origin edits a transaction over a **1,192-row** spending table, closes, edits the next — a full-page-per-row would thrash navigation and lose the user's place; a modal's frozen parent hides which rows remain (`evidence/containers.md`). The repeated-down-a-list shape is the slideover's strongest single signal — list patterns (P-L) reach for it for inline triage.

**P-CN-05. PAGE / ROUTE = a destination: long, multi-step, or content-rich, and the user's MAIN focus. Use a page when the flow has more than ~one screen of content, carries multiple steps, or *is* the task (not an aside to it) — and give multi-step flows a persistent step indicator (a left step-rail or a numbered progress bar).** The page lives in the app shell (or a focused full-screen frame for a wizard).
New. *Why:* a page is the only container with room for a long form *plus* durable progress chrome — every studied wizard carried one (Mercury `1/6` left rail, ElevenLabs step-rail + `Save & exit`, Booking.com numbered bar, Deputy 6-step — `evidence/containers.md`). A modal can't hold 6 steps without becoming a scroll-trap; a slideover can't show "where am I in the flow." Long, multi-step, focus-demanding ⇒ page.

**P-CN-06. PAGE/ROUTE when the flow must be deep-linkable, shareable, or refresh-safe — and the step lives in the URL.** If a user should be able to bookmark it, send the link, resume after a refresh, or use browser back/forward through its steps, it is a route. The route owns the URL; the step is a URL segment or query param (`/onboarding/step-3`, `?step=address`), so refresh and back/forward Just Work.
New. *Why:* deep-link / share / refresh-safe is the one capability overlays *cannot* fake (a modal's open-state dies on refresh) and the page's reason to exist. ElevenLabs' `Save & exit` proves the wizard is a *place you leave and return to* — only possible because its state is in the route, not in transient overlay memory (`evidence/containers.md`). This is the load-bearing factor: when in doubt and the flow needs a URL, it's a page (or a routable overlay — P-CN-07).

**P-CN-07. ROUTABLE-OVERLAY escape hatch: when you want overlay convenience AND a shareable/refresh-safe URL, make the overlay URL-addressable — the parent route owns the URL (`?item=123` / `/orders/123`), the panel owns the view.** The list page reads the param and renders the matching record as a slideover/modal over itself; closing clears the param. Refresh re-opens the overlay; the link opens straight into it.
New. *Why:* this resolves the false choice between "overlay UX" and "linkable URL" — Lookbook already favors **URL-state owned by the route parent** (the DVLA roadworthy `?draft=<uuid>` and activity `?id=` deep-links; the route reads/writes the param, the panel only emits open/close — `feedback-url-state-owned-by-route-parent`). A routable slideover is a real, good pattern; an overlay that *should* be shareable but holds its state in component memory is the forbidden "convenient overlay with no URL."

**P-CN-08. WOULD-IT-NEST-ANOTHER-OVERLAY is the smell that says: make it a page. A flow that wants to open a second modal/slideover from inside the first has outgrown the overlay — promote it to a route.** Modal-on-modal and drawer-spawning-modal stack scrims, trap focus ambiguously, and bury the dismiss path.
New. *Why:* nesting overlays is a reliable signal the flow is a destination wearing an overlay's clothes — it has sub-steps, sub-decisions, or sub-records, which is what pages are for. (A destructive *confirm* fired from within a drawer is the one sanctioned exception — a tiny terminal decision, not a nested flow — P-CN-02.) The fix is almost never "a third scrim"; it's "this should have been a page."

**P-CN-09. Mobile collapse defers to P-MO-09: a modal becomes a bottom sheet (partial for short, near-full-height for tall/search content), a slideover becomes a full-screen sheet or a stacked view — each with a drag handle, a scrim, and a visible dismiss. Do not re-specify the mobile container here.**
Refines: P-MO-09. *Why:* the desktop container choice and its phone form are two decisions; this guide owns the desktop one, `patterns/mobile.md` owns the collapse (every studied mobile dialog was a sheet with handle + scrim + dismiss, never a desktop overlay shrunk — `evidence/mobile.md`). A page stays a page (a full screen in the back-stack, P-MO-06).

**P-CN-10. Every overlay (modal & slideover) ships the accessibility basics: focus moves into the overlay on open and the first focusable / the heading receives it; focus is trapped within while open; `Esc` and a visible close (X / Cancel) both dismiss; a scrim covers the parent; and on close, focus RETURNS to the trigger that opened it.** Focus-visible rings per F34 (2–3px accent ring, offset). A page navigation moves focus to the new page's heading instead.
Refines: F34, F32. *Why:* an overlay that doesn't trap focus leaks keyboard users back onto the frozen parent; one that doesn't return focus on close strands them at the top of the document. Every studied overlay was dismissible (X / Cancel / handle) — none were traps (`evidence/containers.md`, `evidence/mobile.md`). Dismissibility and return-focus are not optional polish; they're the difference between usable and broken for keyboard and screen-reader users.

## Composition defaults
- **Modal**: centered, ~480–560px (single-column) / up to ~640px (a conceptual field-pair), scrim over a dimmed-inert parent, 24–32px inner padding, title row + one-line context, body = the short flow at its own density, footer = ghost Cancel (left or inline) + one filled primary (right), `Esc` + X dismiss, focus trapped, focus returns to trigger.
- **Slideover / drawer**: slides from the right (LTR), ~360–480px (peek/edit) up to ~560px (rich edit), scrim optional-but-preferred over a *visible, in-place* parent, title row + X, body = the medium flow, footer save (sticky if the body scrolls); parent often stays interactive for rapid-repeat (P-CN-04).
- **Page / route**: lives in the app shell (or a focused full-screen wizard frame with `Cancel` / `Save & exit`); multi-step carries a persistent step-rail (left) or numbered progress bar; the step is a URL segment/param (P-CN-06); the archetype's normal content measure (P-F entry-form for create/edit, P-DT for a record).
- **Routable overlay**: the parent route reads `?item=` / a path param and renders the record as a slideover/modal over itself; close clears the param; refresh and direct link re-open it (P-CN-07).
- **Mobile**: per P-MO-09 — modal→bottom sheet (partial vs near-full-height by content), slideover→full-screen/stacked sheet, both with handle + scrim + dismiss; a page stays a full screen in the back-stack (P-MO-06). Don't re-specify here.
- **A11y (all overlays)**: focus-in, focus-trap, `Esc` + visible dismiss, scrim, return-focus-to-trigger, F34 rings (P-CN-10).

## Forbidden moves
- **A long / multi-step / 12-field form crammed into a tiny modal** — past ~5 fields or any step structure, it's a page (P-CN-01/05).
- **An overlay that should be shareable / refresh-safe but isn't routable** — open-state held in component memory, dying on refresh, un-linkable; make it a routable overlay or a page (P-CN-06/07).
- **A destructive action as a full-page navigation** — "Delete?" should block in place as a modal confirm, not navigate the whole app away (P-CN-02).
- **A primary destination demoted to a slideover** — a flow that *is* the user's main, long, or shareable task belongs on a page, not a 400px panel (P-CN-03/05).
- **Modal-on-modal / drawer-spawning-modal** (the one exception: a destructive confirm fired from a drawer) — nesting overlays is the smell that it should be a page (P-CN-08).
- **Two equal-weight buttons in the footer** — one filled primary; Cancel is ghost/text (F16/AP18; P-CN-02).
- **A slideover used to FREEZE the parent** (or a modal used where the user needs the parent live) — the frozen-vs-live distinction picks the container (P-CN-02 vs P-CN-03).
- **An overlay with no dismiss** — no X, no Cancel, no `Esc`, no handle on mobile: a trap (P-CN-10; P-MO-09).
- **Focus that doesn't enter the overlay on open or return to the trigger on close** — strands keyboard users (P-CN-10).
- **A desktop overlay shrunk to 375px on mobile** instead of collapsing to a sheet (P-CN-09; P-MO-09).
- **Per-row full-page navigation for a repeated table edit** where a slideover would keep the user's place (P-CN-04).
